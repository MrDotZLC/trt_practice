> 本文是 `docs/` 的唯一入口：**文档怎么组织、事实写在哪、ID 怎么起**。
> 本文**不记录任何项目状态**——状态一律看 `PROGRESS.md`。
>
> 权威顺序：`AGENTS.md` > 本文（写作规约） > 各文档正文。
> 建立基线（2026-09-27，实测量得）：**本文之外的 21 份**共 13,005 行 / 1012 KB
> （5 份活文档 7766 行 + 16 份冻结文档 5239 行；本文自身不计入这个数）。
> **该基线之后新增的文档不计入**（2026-09-27：`docs/dev/REQ-009-retire-legacy/phase5_development_plan.md`、`interview_summary.md`；2026-10-01：`docs/dev/` 整支）。

> `docs/` 被仓外（代码 / 脚本 / 根 `README.md`）引用 **79 行 / 37 个文件**（已排除 `third_party/`）。

## 1. 先读什么（新会话阅读顺序）

1. `PROGRESS.md` 顶部的「当前基线」块 —— 现在在哪、测试基线是多少。
2. `PROGRESS.md` §6.6「当前未解决项」—— 哪些事还活着（它只是索引）。
3. 命中某条开放项 → `future_iterations.md` 的对应条目（目标 / 触发条件 / 前置 / 验收判据）。
4. 决定动手 → 先走 `AGENTS.md` §5「计划对账」；开发状态与设计在 `docs/dev/<feature>/`
   （入口 `STATE.md`），用例与判据在该条目的 `test_plan.md`（2026-10-01 之前立项的老条目
   仍在 `future_iterations_test_plan.md`）。
5. 遇到故障、或要查某条结论的来路 → `TROUBLESHOOTING.md` 顶部的索引表。
6. 只要设计思路 → `mini_trt_llm_design.md`；只要某阶段的判据出处 → 对应的 `phaseN_*.md`。

> **不要从 `phase0` ~ `phase4` 的任何一份文档开始读。** 那 16 份全部已交付并冻结，
> 只作设计与判据出处，里面的"待办"早已过期。

## 2. 文档地图

### 2.1 活文档（5 份：描述现状或当前工作，随项目更新）

| 文档 | 角色 | 读它的时机 |
|---|---|---|
| `PROGRESS.md` | 现状 / 架构决策 / 已知坑结论 / 开放项索引 | 接手项目的第一份 |
| `TROUBLESHOOTING.md` | 排查证据（现象 / 命令 / 日志 / 对比数据），append-only | 要查某条结论怎么来的，或自己刚踩了坑 |
| `future_iterations.md` | 开放项的唯一事实来源：是什么 / 触发条件 / 前置 / 判据 / 优先级 | 想知道"还能做什么、什么时候才做" |
| `future_iterations_development_plan.md` | 条目化计划的"怎么做"：任务分解 / 接口 / 破坏性清单（**含已执行条目的安排与回填**） | 拿到批准、准备动手时 |
| `future_iterations_test_plan.md` | 条目化计划的"怎么验"：用例 / 判据 / 出处 / 环境（含结果回填） | 写用例、或裁决"算不算过"时 |

### 2.2 冻结文档（只作设计与判据出处）

**留在本层的 1 份**：`mini_trt_llm_design.md`（架构设计总纲）。

**已按功能迁入 `docs/dev/` 的 16 份**（2026-10-01）：原 `phase0_*` ~ `phase5_*` 的开发计划与测试计划，
现各自收在对应条目目录里，**文件名不变**（锚点 ID 如 `PH2-*` 继续有效）。清单见 `dev/INDEX.md` §5。

冻结口径见 §7。**这些文档里的"待办 / 待回填 / 下一步"一律不代表现状**；每个条目的**现行陈述**
以其 `requirement.md` / `design.md` / `test_plan.md` 为准。

### 2.3 材料类（1 份：**不参与 SSOT**）

| 文档 | 角色 | 读它的时机 |
|---|---|---|
| `interview_summary.md` | 面试口径的项目材料，**按面试官提问顺序组织**（介绍项目 → 亮点深挖 → 系统问题 → 最难的问题 → 用 Codex 怎么开发；附录为功能清单 / 数字表 / 剩余问答） | 准备面试、或需要"对外口径"时。**不新增技术结论**，数字与判据仍以 `PROGRESS.md` 等为准 |

### 2.4 开发状态（`docs/dev/`：技能产出的开发 artifact）

入口是 `dev/INDEX.md`（全部条目一览），每个 feature 目录里 `STATE.md` 是该条目状态的唯一落点；
文件构成、阶段链与 Gate 见技能 `trt-inference-engineering` 与 `AGENTS.md` §5，本文不复述。
状态数字仍只有 `PROGRESS.md` 一个出处。

条目目录一律命名为 `REQ-NNN-<slug>`（**编号只承载身份，不承载状态**）。
**未触发与冻结的需求不进编号**——它们由 `future_iterations.md` 自己保存，被点名开工时才建目录。

条目分两类：**进行中**（按技能流程推进）与**历史**（2026-10-01 起需求回填，`status = completed`，
不代表仍在推进）。**过渡期权威**：同一需求同时存在于本目录与历史文档时，**以本目录为准**；
历史文档在删除前只作快照，**删除是最后一步且需单独批准**。

> 项目总入口是根目录 `README.md`；本文只负责 `docs/` 内部的组织规则。

## 3. 事实归属（SSOT：一个事实只写一次）

每类事实只有一个落点，其他地方**只放指针，不复制内容**。

| 事实类型 | 唯一落点 | 其他文档怎么写 |
|---|---|---|
| 现在在哪、测试基线、版本号、产物尺寸 | `PROGRESS.md` 的「当前基线」块 | 只写"见 `PROGRESS.md` 当前基线"；**不复制数字** |
| 架构决策与"为什么选 A 不选 B" | `PROGRESS.md` §2 | 链接 |
| 已交付了什么 | `PROGRESS.md` §3 | 链接 |
| 已知问题 / 坑的**结论**（问题 / 影响 / workaround） | `PROGRESS.md` §5 | 链接；**过程不写在这里** |
| 排查过程（命令 / 日志 / 对比数据 / 被否证的假设） | `TROUBLESHOOTING.md` | 只写 `TS-xxx` |
| 还没做什么 / 触发条件 / 优先级 | `future_iterations.md` | 只写 `OI-xxx` |
| 某个 feature 的**开发状态**（在哪个 Phase、卡在哪、下一步） | `docs/dev/<feature>/STATE.md`（**真值**）＋ `docs/dev/INDEX.md` §1（**唯一允许的快照副本**） | `PROGRESS.md` 只写人话 + 链接，**不复制 phase / status 值**；快照与 STATE 不一致时以 STATE 为准（校验脚本 `mini_trt_llm/tools/check_docs_index.py`） |
| 怎么做（任务分解 / 接口 / 破坏性清单） | `future_iterations_development_plan.md` | 链接 |
| 怎么验（用例清单 / 判据 / 执行口径） | `future_iterations_test_plan.md` 或对应 `phaseN_test_plan.md` | 链接 |
| 阈值本身 | 用例代码里阈值所在处（**原地写清出处**，AGENTS.md §7） | 只写出处链接 |
| 阈值的出处（哪次实测 / 哪个标准 / 哪份文档） | 该用例所属的**测试计划** | 链接 |
| 开工纪律 / 证据纪律 / 权限规则 | `AGENTS.md` | **不复述**，写"见 `AGENTS.md` §x" |

三条配套纪律：

- **数值类状态只能有一个出处。** 同一个基线数字出现在两份文档里，必然有一份先过期
  （本项目已因此吃过一次：旧总数 242 / 243 / 235 / 259 与现状 264 同时存在于 `PROGRESS.md`）。
- **纪律条款不复述。** 文档里重写一遍 AGENTS.md 的规则，改一次口径就要改 N 处。
- **结论与过程分家。** `PROGRESS` 只留结论 + 指向 `TROUBLESHOOTING` 的 ID；过程细节不进 PROGRESS。

## 4. 编号规约

### 4.1 为什么需要规约（实测冲突）

| 冲突 | 表现 |
|---|---|
| `P2` 双义 | 优先级 P2 vs 阶段任务 `P2-1` |
| `D1`~`D5` 多义 | phase1 / phase2 / phase3 / phase4 / future_iterations 各自独立定义，全仓 196 处 `Dn` 无法全局解析 |
| `§2.2` 双义 | `PROGRESS.md` 里是"定位：多模态框架"，`future_iterations.md` 里是"FlashAttention" |
| `S` 双义 | 沙箱测试层 S 层 vs 用例号 `S-14` |
| `B1-4` vs 批次 B | 真机用例号 vs 开发批次 |

根因是**跨文档引用只写 `§3.0j` 而不写文件名**——读者必须打开文档才知道指向什么，
于是章节编号一旦重排引用全部失效，编号被迫冻结。

### 4.2 规则

- **R1** 跨文档引用必须写成 `文件 + ID`，例如 `PROGRESS.md + DEC-INT8-WEIGHT-SOURCE`。
  **禁止**在跨文档语境里只写 `§3.0j` 或 `#46`。
  **存量豁免**：已经点名了目标文档的引用（如 `` 见 `PROGRESS.md` §2.13 ``）视为合规，**不强制回改**。
  2026-09-27 实测这类有 651 处，为"好看"批量重写只会制造没有信息量的 diff。
- **R2** `§` 只用于**同一文档内**导航，写法不变。
- **R3** **被跨文档引用过的标题**，在标题文本前置 `[ID]`；没被引用的标题不强制。
- **R4** ID 由"大写英文 + 短横线"组成，含义自明。**禁止** `ID-1`、`ITEM-A` 这类无语义编号。
- **R5** 老编号**保留在标题文本里**，让既有的 1627 处 `§` 引用继续可以搜到。
  **只加不改，不做批量重命名。**
- **R6** ID 的位置固定在**编号之后**：`### 3.0j [DEC-INT8-WEIGHT-SOURCE] 结案：…`。
  理由是保住 `^#{2,3}\s+号码` 这类既有检索方式——ID 放到最前面会把它们全部打断。

> **批 2 已收尾（2026-09-27）**：147 个被引用过的标题已挂 ID；**新写的跨文档引用一律用
> `文件 + ID`**。存量里"已经点名了目标文档"的 `§` 引用按 R1 的存量豁免保留（本文正文中出现的
> `PROGRESS.md §6.6` 之类即属此类），不强制回改。

### 4.3 前缀表（全仓唯一）

| 族 | 前缀 | 例子 | 归属文档 |
|---|---|---|---|
| 决策 / 结论锚点 | `DEC-` | `DEC-INT8-WEIGHT-SOURCE` | `PROGRESS.md` |
| 排查条目 | `TS-` | `TS-046` | `TROUBLESHOOTING.md` |
| 开放项 | `OI-` | `OI-INT8-ABS` | `future_iterations.md` |
| 计量点 | `MP-` | `MP-005` | 计划 / 测试文档 |
| 缺口 / 门 | `GAP-` | `GAP-G5` | `future_iterations.md` |
| 冻结阶段文档锚点 | `PH<n>` | `PH4-INT8-CRITERIA`、`PH1.5-ACCEPTANCE` | `phaseN_*.md` |
| 冻结设计文档锚点 | `DESIGN-` | `DESIGN-NATIVE-BUILD` | `mini_trt_llm_design.md` |
| **需求编号** | `REQ-` | `REQ-017`（目录名 = `REQ-NNN-<slug>`） | `docs/dev/INDEX.md` |

> **`OI-` 的存量例外（2026-10-05 补）**：**新增**的开放项编号只允许定义在 `future_iterations.md`；
> 但 2026-09-26~27 那批把"计划段 / 用例段"也各自编了 `OI-*` 号——**共 16 个定义在
> `future_iterations_development_plan.md` / `future_iterations_test_plan.md`**。这些存量编号
> **不改名**（§4.2 的存量豁免），落点映射见 `future_iterations.md` §0.4。

### 4.4 保持原样的本地编号

下列编号**不做全局唯一化**：它们在各自的文档语境里已无歧义，重命名是纯 churn。

- 阶段任务：`P0-1` ~ `P4-8`、`P1.5-0` ~ `P1.5-7`
- 用例号：`E1`~`E4`、`S-14`、`L0`~`L3`、`B1-4`、`T1`~`T3`
- 决策项：`Q1`~`Q15`、`F1`~`F4`、各阶段的 `Dn`
- 计量点旧名：`PF-n`、`PP-n`
- **技能流程阶段**：`P0-Requirement` ~ `P9-Interview`（feature）、`B0-Reproduce` ~ `B4-Summary`（bugfix）、
  里程碑 `S1`/`S2`/`S3`——**只允许出现在 `docs/dev/<feature>/` 内**。它们与优先级 `P0`~`P3`、
  验收条目 `B1`~`B4`、用例号 `B1-4` **不是同一族**；跨文档引用必须写成"文件 + 阶段名"。

**条件**：跨文档使用这些编号时，必须同时写出它所属的文档名（R1 已覆盖），不得只丢一个裸编号过去。

### 4.5 怎么找出"必须挂 ID"的标题

```bash
# 粗筛：列出所有跨文档出现的 § 目标，人工确认归属后再挂 ID
rg -n --no-heading '§[0-9]+(\.[0-9]+)*' docs/*.md | sort -u
```

判定标准：**被别的文档或代码引用过的标题**才挂 ID；同一份文档内部的导航不需要。

### 4.6 代码注释里的 docs 引用（2026-09-27 起，2026-10-01 补齐）

代码 / 脚本 / 构建脚本里引用 `docs/` 时与正文同规则：**路径 + ID**（`docs/TROUBLESHOOTING.md + TS-046`）。
2026-09-27 把**当时那批 69 行 / 35 个文件**（含 `src/core/`、`src/plugins/`、`include/`）里的
`§N` / `#N` 换成 ID 形式。**更正（2026-10-01）**：原文写的是"全部换成"——复扫发现**仍有 121 处
`#NN`，其中 27 处该行及其 ±3 行上下文完全没写文档名**（读代码的人无从判断是哪份文档的哪一条）。
这 27 处已全部补成 `` `docs/TROUBLESHOOTING.md` + TS-0NN ``（14 个不同 ID，均在排查记录里），
**孤立引用归零**；"全部换成"这个说法只对当时那批成立，以本段为准。

**两个坑**：① **有耦合的运行期字符串**——`thresholds["provenance"]` 同时出现在

## 5. 引用写法（照抄即可）

```text
✅ 见 PROGRESS.md + DEC-INT8-WEIGHT-SOURCE
```

## 6. 预算（超过就触发一次瘦身）

**例外（2026-10-05）**：`PROGRESS.md` 改按**总行**考核、且**不再使用 `<details>`**——它的
历史叙述已归各条目 `summary.md` 与 `TROUBLESHOOTING.md`；其余文档仍按可见行。

| 文档 | 现值（总 / 可见） | 上限（可见） | 超限动作 |
|---|---|---|---|

## 7. 冻结与归档

> **例外（2026-09-27 起）**：冻结文档里**与现行决定直接冲突**的表述，允许**加日期批注修正**

## 8. 变更流程（改文档也照这个走）

3. 改完自检：没有裸 `§` / 裸 `#` 跨文档引用；新增 ID 与 §4.3 前缀表一致。
4. 数值基线只改 `PROGRESS.md` 当前基线那一处；规约本身要改就改本文并在提交信息里说明理由。
