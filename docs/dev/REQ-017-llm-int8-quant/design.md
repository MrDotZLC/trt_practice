# Design

## Overview

分两个里程碑：

| 里程碑 | 内容 | 是否本轮 |
|---|---|---|
| **S1 权重量化** | GPT-2 以 INT8 权重端到端跑通，含自证与数值判据 | 是（Gate-A 后） |
| **S2 K/V 缓存量化** | cache 元素宽度可配 + 插件支持低精度 cache | 由 Gate-A 决定（见 D3） |

S1 内部先做"能跑 + 能自证 + 有判据"，再做"省了多少"的量化对比。

## Architecture

S1 选**原生图内量化**（D1 = A）时的结构：

```text
safetensors 权重
      ↓ 读取（现有）
 量化参数（离线算好的 scale，随权重一起加载）
      ↓
 ┌────────────────────────────────────────┐
 │ 原生建图（语言模型）                     │
 │  权重 → INT8 常量                        │
 │       → 反量化节点（输出 FP16/FP32）      │
 │       → MatMul / Gemm（与 DQ 融合）      │
 └────────────────────────────────────────┘
      ↓
 引擎（可用引擎检查器读出逐层精度自证）
      ↓
 运行时（精度契约不变：向引擎查询）
```

## Module Design

| Module | Responsibility | Dependency |
|---|---|---|
| 量化参数产物（新增） | 每层权重的 scale（per-tensor 或 per-channel），与模型配置一同提供 | 离线量化脚本 |
| 量化脚本（新增，Python） | 从 FP32 权重算出 scale，落盘为可复现产物（含来源哈希） | 现有转换工具链 |
| 语言模型构建器 | 权重常量改为 INT8 + 反量化节点 | 量化参数产物 |
| 构建配置 | 新增"权重量化"开关与粒度（不动现有精度档位语义） | — |
| 引擎检查器护栏（复用） | 把"量化层确实以低精度执行"变成用例断言 | 已有的逐层精度开关 |
| 运行时 | **尽量不改**：精度契约仍是"查询引擎" | — |
| 分页缓存 / 注意力插件 | S2 才改（元素宽度） | — |

## Data Structure

```text
QuantSpec {                       // 每层一条，落在模型目录里
    std::string tensor_name;      // 权重名（与配置里的名字映射一致）
    enum Granularity { kPerTensor, kPerChannel };
    int32_t channel_axis;         // per-channel 时有效
    std::vector<float> scales;    // per-tensor 时长度为 1
}
```

要点：**scale 与量化对象必须是同一份张量**。视觉模型侧踩过的坑是"scale 取自未折 BatchNorm
的权重、而量化对象是已折 BN 的权重"（`docs/PROGRESS.md` §3.0j / `docs/TROUBLESHOOTING.md` #46）。
语言模型没有 BN，但存在同类风险：**若权重在建图期做过任何变换（转置、合并 QKV、绑定词表），
scale 就必须在同一个变换之后算**。这一条要在 P6 用文件级证据锁住。

## Runtime Flow

```text
[P4 基线] FP32 引擎 → 量：引擎体积 / 显存 / 每步延迟
      ↓
[P5 实现] 算量化参数 → 建 INT8 引擎 → 自证逐层精度
      ↓
[P6 测试] 同 prompt 同 seed：INT8 vs FP32
      ├─ 逐 token 一致率
      └─ prefill logits 相对偏差
      ↓
[P7 基准] 同 session、同二进制、逐轮交替 → 延迟与显存对照
```

## Resource Lifecycle

| 资源 | 何时创建 | 何时释放 |
|---|---|---|
| 量化参数（host） | 构建期读入 | 构建结束 |
| INT8 权重常量 | 构建期（TRT 持有） | 引擎析构 |
| 反量化输出张量 | 构建期由 TRT 规划 | 引擎析构 |
| 引擎缓存（磁盘） | 构建后落盘，指纹含精度与开关 → 换配置自动重建 | 手动删除 |
| 运行时缓冲 | **不变**（仍按引擎声明的边界精度分配） | 析构 |

要点：运行时**不应**因为量化而新增任何 buffer 逻辑——这是选择"让 TRT 在图上做 DQ"的理由之一。

## Performance Consideration

- **compute**：本机无 Tensor Core，INT8 不会带来张量核心吞吐；若 DQ 与矩阵乘融合不良，
  反而可能因为额外的类型转换而变慢。
- **memory（主要收益）**：权重字节数从 4 → 1，decode 每步的权重读取量下降到约 1/4。
  这是本机唯一能立得住的收益来源。K/V 缓存目前是 2 字节，量化到 1 字节再省约一半缓存占用。
- **显存（次要收益）**：6 GB 卡上，权重占用下降会直接抬高可用的批 / 上下文上限
  （与 `REQ-016-continuous-batching` 的容量上限互为因果）。
- **测量口径**：沿用既有协议（同 session、同二进制 A/B、逐轮交替、报中位数与四分位、
  先给判别下限）。**必须报"每步延迟"而不是只报"每 token 吞吐"**，因为 decode 的收益
  表现为每步更快而不是并发更高。

## Trade-off

### D1 量化落地路线

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 原生图内量化（推荐）** | 语言模型构建器里把权重常量换成 INT8 + 反量化节点 | **自包含、不依赖任何其他 feature**；缺点是要自己算 scale 并维护量化产物 |
| B. 外部图量化（ONNX Q/DQ） | 复用视觉模型那套工具链 | 工具链成熟，但**ONNX 路径当前没有 decode 图与 K/V 输入**，端到端要依赖 `REQ-019-onnx-subgraph`；且要先解决 §10.1 的 I/O 契约 |

**决策：A 先行**。B 在 `REQ-019-onnx-subgraph` 落地后作为第二条路线复评（届时可做
"同模型、两种量化路线"的对照，本身就是很好的结论）。

### D2 量化粒度

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. per-tensor（先做）** | 每个权重一个 scale | 简单、可解释；精度损失略大 |
| B. per-channel | 每个输出通道一个 scale | 精度更好；多一份通道轴处理，且**必须先证明 scale 来源与量化对象一致** |

**决策：先 A 后 B**，且 B 必须在 A 的判据体系跑通之后再做——否则出了偏差分不清是粒度问题
还是实现问题（视觉模型侧正是在这一点上被"产图脚本取错源"骗过一次）。

### D3 K/V 缓存量化

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 本轮只做权重 | 改动面限于构建期 | 收益集中在权重读取；缓存仍是 2 字节 |
| **B. 权重 + 缓存分两阶段** | S2 单独做缓存 | 缓存量化要动：cache 元素宽度、注意力插件元素白名单、写 K/V 的转换路径、运行时的精度校验——**四处**，且每一处都影响数值 |

**决策：本轮只做权重；缓存量化作为 S2 单独评审。** 理由：两者混在一起会让数值偏差无法归因，
这与项目在 split-K 上"不把两个变量混在一起"的做法一致。

### D4 判据

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 复用视觉模型的阈值 | 省事 | **禁止**：跨精度 / 跨口径复用（`AGENTS.md` §7） |
| **B. 先量基线再定（推荐）** | P4 量出 FP32 自身的构建间波动，P6 用同 session 对照 | 慢一点，但判据能回答"凭什么" |

## Risk

| 风险 | 影响 | 缓解 |
|---|---|---|
| scale 与量化对象不是同一份张量 | 精度静默崩坏，且看起来像"TRT 不行" | 沿用 §3.0j 的排查法：文件级证据（饱和比例）+ 探针（量化前张量） |
| DQ 未与矩阵乘融合 | 变慢而非变快 | 先看逐层精度自证，再测延迟；不融合就不上 |
| 精度档位语义被稀释 | 现有 FP16/FP32 行为被改坏 | 新增独立开关，不动现有档位语义 |
| 判据阈值来路不明 | 违反 §7 | 阈值出处写进用例与测试计划 |
| 6 GB 显存不足 | 大上下文下构建失败 | 先量 FP32 的显存占用，再定目标 |
