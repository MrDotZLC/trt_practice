# Design

> **性质**：历史设计回填（2026-10-01）。从 `docs/dev/REQ-009-retire-legacy/phase5_development_plan.md` §2 资产盘点 /
> §4~§7 各阶段抽取，**未新增当时的决定**。

## Overview

把两个历史示例工程从仓库路径下线。核心不是"删目录"，而是**先让覆盖损失可见**，再迁移，最后删除。

## Architecture

```text
阶段 0 让覆盖损失可见（纯新增）
   资产闸门（缺资产→判失败）＋ 期望跳过集合基线 ＋ 闸门自证用例
        ↓
阶段 1 资产迁移（行为零变化）
   四类资产搬到 assets/legacy/；过渡期用相对软链接保证代码与 provenance 零改动
        ↓
阶段 2 解除"借别的模型产物当负例夹具"的耦合
        ↓
阶段 3 删除源码目录（逐条批准）
        ↓
阶段 4 真机验收 + 文档回填
```

## Module Design

| 阶段 | 关键做法 | 为什么 |
|---|---|---|
| 0 | 资产闸门做成**宏**而非函数 | 跳过 / 失败的断言宏展开后都是 `return`，封装成函数只会退出那个函数，用例体会继续往下跑 |
| 0 | 期望跳过集合钉成**清单文件** + ctest 比对项 | 用集合而非条数——本计划的坑正是"条数不变、用例换人" |
| 0 | 给闸门本身加正反用例 | 护栏没有用例证明"它会拦人"就等于没有护栏 |
| 1 | 资产迁移 + 相对软链接过渡 | 让同批的代码路径与来源记录**一行都不用改**，把"迁移"与"改代码"两个风险源拆开 |
| 3 | 删除 22 个跟踪文件 + 根构建里的旧模块注释 + 4 条软链接 | 让目录彻底消失；连带 20 处路径改到新位置 |

## Data Structure

```text
assets/legacy/
├── resnet18_onnx/     ← 图 + 校准数据（500 张，保持原文件名）
├── gpt2_onnx/         ← 图 + 唯一的精度基线
├── scripts/           ← 三个重建脚本（按 __file__ 定位输出目录）
└── README.md          ← 来源 / 获取方式 / 哈希 / 重建命令 / 为什么留着
```

## Runtime Flow

```text
删前：用例读旧路径 → 命中资产 → 执行
删后：用例读新路径 → 命中资产 → 执行（跳过集合逐条不变）
缺资产：闸门开启 → 判失败（而不是静默跳过）
```

## Resource Lifecycle

- 资产不入库（体积大），由 `assets/legacy/` 的说明与脚本负责重建；
  **校准数据不可离线重建**（需联网下载），因此它的存续是硬约束。
- 引擎缓存删除后首次运行会重建（分钟级，属预期）。

## Performance Consideration

不涉及性能；代价是删除后首次运行需重建引擎。

## Trade-off

| 决策 | 选择 | 为什么 |
|---|---|---|
| 先加闸门还是先迁资产 | **先闸门** | 不做这一步，后面任何删除都无法验证——覆盖损失对 CI 不可见 |
| 迁移期是否直接改路径 | **先用相对软链接过渡** | 把"迁移"与"改代码"拆成两步，跳过集合才有干净的对照 |
| provenance 字符串 | **改到新路径，哈希不动** | 内容是同一份文件换了位置；哈希才是真身份 |
