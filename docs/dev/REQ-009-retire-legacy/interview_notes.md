# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"一次'删代码'的任务，难点却全在**看不见的地方**：两个老目录里的数据资产还是现行测试的判据来源，
直接删会让用例静默跳过——而跳过在 CI 里算**通过**。所以顺序必须是：先让损失可见，再迁资产，最后删。"

## Architecture Explanation

```text
资产闸门（缺资产判失败）→ 期望跳过集合基线 → 迁资产 → 删目录 → 真机验收
```

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 闸门形态 | **宏**，不是函数 | 跳过/失败的断言宏展开后都是 `return`，函数封装只会退出那个函数 |
| 基线口径 | **集合**，不是条数 | 本计划的坑正是"条数不变、用例换人" |
| 迁移过渡 | **相对软链接** | 把"迁移"与"改代码"两个风险源拆开 |
| 来源记录 | 改路径、**哈希不动** | 同一份文件换了位置；哈希才是真身份 |

## Technical Challenges

1. **静默跳过是 CI 的盲区**：改名实验证明，删掉资产后 ctest 仍报"100% passed"。
2. **闸门本身要有用例**：没有正反用例证明"它会拦人"，就不算护栏。
3. **静态分析会漏**：有条自检对资产的依赖写在构建脚本的测试参数里，grep 测试源码抓不到。

## Trade-offs

- 多花一个"阶段 0"（纯新增、不改行为）→ 换来后续删除**可验证**。
- 资产保留在新位置而不是删掉 → 换来可重建，代价是仓库里仍有几百 MB 本地资产（不入库）。

## Interview Questions

### Level 1

Q：为什么不能直接删？　A：资产还在被测试用；删了会让用例静默跳过，覆盖损失不可见。

### Level 2

Q：怎么知道覆盖没丢？　A：用"跳过集合逐条不变"作判据——集合，不是条数。

### Level 3

Q：闸门为什么写成宏？　A：断言宏展开是 `return`，封装成函数只会退出函数、用例继续往下跑。

### Level 4

Q：怎么证明闸门有效？　A：从空目录跑一条依赖资产的用例：不设闸门→跳过；设闸门→判失败（反向断言）。

### Level 5

Q：这次最反直觉的发现？　A：**ctest 把 Skipped 记作 Passed**——删掉一批用例的资产，它仍报 100% 通过。

## Follow-up Questions

- 资产能重建吗？（多数能；**校准数据不能**，需联网，所以必须保留）
- 删除范围谁定？（作者逐条批准；"这东西没人用"的判断不归工具，见 `AGENTS.md` §0.6）
