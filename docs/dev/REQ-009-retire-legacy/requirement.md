## Problem

仓库里还留着两个早期的示例工程目录。它们已经不再参与构建，但其中的**数据资产**仍是现行
测试的判据来源。直接删会连带丢掉资产；不删则路径上始终留着两套过时结构。
更关键的是：删掉资产后，相关用例会**静默跳过**，而跳过在 CI 里表现为通过——
覆盖损失对流水线不可见。

## Goal

让仓库路径里不再出现那两个历史目录，同时满足三条硬约束：

1. **不丢任何判据**——现有用例的覆盖面不减少；
2. **覆盖损失必须可见**——不许把"用例没了"变成"静默跳过"；
3. **资产仍可重建**，且重建入口在仓库里有明确位置。

## Scope

### Included

- 让"资产缺失"从静默跳过变为显式失败（资产闸门）。
- 资产迁移并验证"跳过集合逐条零变化"。
- 解除"借别的模型产物当负例夹具"的耦合。
- 删除两个历史目录及其过渡用软链接。
- 真机全量验收与文档回填。

### Excluded

- 不恢复旧模块的构建。
- 不改动旧模块的业务逻辑（它们不参与构建，改逻辑没有收益）。
- 不重算任何基线数字。

## Acceptance Criteria

来源：`docs/dev/REQ-009-retire-legacy/phase5_development_plan.md` §9（4 条，每条都写明"凭什么"）。

1. 资产迁移后，沙箱**跳过集合逐条不变**（用集合而非条数——本计划的坑正是"条数不变、用例换人"）。
2. 目录删除后，真机跳过集合 = 阶段 0 钉住的基线；删除的唯一可接受后果是"零变化"。
3. 资产闸门本身**有正反用例**（护栏没有用例证明"它会拦人"就等于没有护栏）。
4. 重建脚本在仓库内可定位（"可重建"只写在文档里、脚本却删了，等于不可重建）。

## Constraints

- **执行顺序是承重的**：先加闸门 → 再迁资产 → 最后删目录。顺序反了，"覆盖损失可见"这条就不成立。
- 删除动作必须逐条确认（每个具体动作单独批准），不能因为"看起来琐碎"而合并。
- "某个文件还有没有人在用"的判断归作者，不归工具——代码里查不到引用不等于安全。
