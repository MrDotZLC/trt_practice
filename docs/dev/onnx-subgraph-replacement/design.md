# Design

## Overview

整条 feature 被一个**前置门**卡住：PF-7 未跑之前，"替换"没有可论证的目标。

```text
PF-7（真机对照：外部图 vs 原生，≥3 次构建 / ≥20 次推理）
   ├─ 结论：外部图显著更慢 → 进 S1
   └─ 结论：无显著差异     → 停止，记录结论并关闭本条（有价值的结果）
        ↓ S1 识别升级（计数 → 拓扑）
        ↓ S2 替换落地（含自定义算子导出）
        ↓ S3 契约统一（两条路可互换调用）
```

## Architecture

S2 采用"图侧重写"时的新增环节：

```text
ONNX 文件
   ↓ ① 拓扑级识别（找出目标子图的边界：入口张量、输出张量、内部算子集合）
   ↓ ② 图重写（用**自定义域算子**替换整个子图，保留原输入输出名）
   ↓ ③ 解析（解析器遇到自定义算子 → 查插件注册表 → 创建插件）
   ↓ ④ 契约检查 + profile + 构建 / 序列化
   ↓
引擎（自研算子被真正执行）
```

## Module Design

| Module | Responsibility | Dependency |
|---|---|---|
| 识别（拓扑级） | 找出子图的入口 / 出口 / 内部算子集合，并拒绝"计数相同连接不同" | 现有识别脚本 |
| 图重写（新增） | 用自定义算子替换子图，保持外部 I/O 名字不变 | 图解析库 |
| 自定义算子导出（前置） | 让导出侧能产出带自定义域的算子 | `future_iterations.md` §6.2 |
| 插件注册表 | 解析时按域名 + 算子名找到创建器 | 已有，需确认域名匹配规则 |
| 一致性对拍用例 | 替换前后同输入对比 | 现有对拍用例 |
| 契约统一 | 两条路输入元素类型与位置编码输入对齐 | `future_iterations.md` §10.1 |

## Data Structure

```text
SubgraphBoundary {
    internal_nodes;   // 要被替换掉的算子
    inputs;           // 边界输入张量名（保持原名）
    outputs;          // 边界输出张量名（保持原名）
    target_op;        // 替换成的自定义算子
}
```

要点：**替换只动内部，不改边界张量名**——名字一改，外部契约与所有下游引用都要跟着改，
也会让"替换前后对拍"失去共同基准。

## Runtime Flow

```text
原图   ──→ 引擎 A（未替换）──┐
                              ├─ 同一输入 → 比数值（相对界，注明出处）
重写图 ──→ 引擎 B（已替换）──┘
                              └─ 同一 session → 比延迟（PF-7 同款协议）
```

## Resource Lifecycle

| 资源 | 变化 |
|---|---|
| 重写后的图文件 | 新产物，与模型一起落盘（不入库，按既有规则） |
| 引擎 A / B | **两条缓存路径必须分开**，否则会互相判过期、来回重建（项目踩过这个坑） |
| 插件实例 | 由解析器创建，随引擎生命周期管理；反序列化路径必须能重建 |
| 临时张量 | 替换不引入额外运行时分配 |

## Performance Consideration

- **compute**：替换本身不改变计算量，改变的是"由谁执行"（原生层 → 自研算子）以及融合机会。
  自研算子会**打断融合**，可能变慢——这正是必须先测的原因。
- **memory**：自研算子引入的中间张量可能抬高峰值占用。
- **测量协议**：必须沿用既有 G6 口径（同 session、同二进制、≥3 次构建 / ≥20 次推理、
  报中位数与极差、先给判别下限）。**跨 session 的数字不可比**（项目已有实测教训）。
- 本机能力边界：拿不到逐 kernel 时间线 → 只能用端到端与斜率口径，不能用"某算子省了多少"来论证。

## Trade-off

### D1 要不要做

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 先跑 PF-7 再决定（推荐）** | 用可复现对照决定方向 | 多一次真机往返；但避免为一个不存在的收益写代码 |
| B. 直接做替换 | 认为"自研算子一定更快" | 与两次反向测量矛盾；做完可能发现整体更慢 |

**决策：A。** 若 PF-7 显示无显著差异，"不做替换"是合法且应当记录的结论。

### D2 替换在哪一侧做

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. Python 侧图重写（推荐）** | 在图上完成替换，导出带自定义算子的新图 | 工具链成熟、可离线、可进 CI 的 host 用例；替换逻辑可见可测 |
| B. C++ 侧网络变换 | 在解析后的网络上定位并重建算子 | 没有通用子图替换原语，要按名找层、逐张量重连；**脆弱且难测**，图结构一变就可能静默错连 |

**决策：A。** B 只在"只有引擎、没有源图"的场合才有意义，本项目不需要。

### D3 替换哪些子图

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 三个自研算子都替换 | 听起来最完整 | GPT-2 里**不存在**旋转位置编码与 RMSNorm；LayerNorm 用原生层已足够 → 大部分是空转 |
| **B. 只替换注意力子图（推荐）** | 目标模型上唯一有实际意义的可替换面 | 范围小，但"为什么只替换这一个"能答得清楚 |

### D4 自定义算子怎么进图

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 导出时注册符号映射 | 由导出脚本产出自定义域算子 | 需要维护一套符号映射；但对上层模型代码透明 |
| **B. 图重写时直接构造自定义算子节点（推荐）** | 在重写阶段产出 | 不依赖上游导出行为，替换逻辑自包含 |

## Risk

| 风险 | 影响 | 缓解 |
|---|---|---|
| PF-7 结论是"无差异" | 整条 feature 失去目标 | 提前接受这个可能；把它当成有效结论记录 |
| 自研算子打断融合后更慢 | 做了负收益的改动 | 先 PF-7，再逐子图 A/B；不达标不上生产路径 |
| 图重写改动了边界张量名 | 下游引用全断、对拍失去基准 | 把"边界名不变"写成断言，用 host 用例锁住 |
| 识别升级后基线变化 | 现有护栏误报 | 保留原计数基线，新增拓扑判据，二者都要过 |
| 两条引擎缓存互相判过期 | 来回重建，分钟级浪费 | 两条路径独立命名（已有先例与教训） |
| 契约不统一 | 接了运行时也跑不起来 | 把 §10.1 作为 S3 的显式验收项，而不是"顺手做掉" |
