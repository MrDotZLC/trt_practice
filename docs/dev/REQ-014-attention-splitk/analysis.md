# Analysis

> **性质**：历史分析回填（2026-10-01）。来源：本目录 `future_iterations_development_plan.md` §12.1 / §12.2。

## Current Architecture

实测显示：上下文变长时，解码每步的时间几乎线性增长，且**注意力占每步绝大部分**
（性能画像条目量出的结论）。机制是：每层可并行的块数（头 × 批）远少于硬件并行度，
每个块要**串行走完整个上下文**，有效带宽只有峰值的一小部分。

## Data Flow

```text
stage-1（头 × 批 × 分片）：每块算一段连续逻辑位置的局部 m / l / acc（float 累积）→ workspace
stage-2（头 × 批）：M = max m；l = Σ l·exp(m−M)；acc = Σ acc·exp(m−M）→ 输出 acc / l
```

## Relevant Modules

| 模块 | 开工时状态 |
|---|---|
| decode 注意力 kernel | 单趟：每块串行走完整段上下文 |
| 分片策略 | 不存在 |
| 工作区契约 | 存在（尺寸按动态形状上界） |
| A/B 入口 | 旧单趟实现保留 |

## Existing Limitations

1. 长上下文下注意力是每步的主要成本，且随上下文线性增长。
2. 并行度只到（头 × 批），上下文维没有并行。
3. 宿主侧拿不到当前上下文长度 → 不能"短上下文自动走单趟"。

## Extension Points

- **上下文维分片**：把"串行走完"改成"分段并行 + 两阶段归约"。
- **分片策略纯函数**：主机与设备共用同一份切法，便于离线单测。
- **workspace**：按动态形状上界申请，是任一并行方案的通用前提。
