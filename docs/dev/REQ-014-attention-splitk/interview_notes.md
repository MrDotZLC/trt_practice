# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。这是本项目**自研 kernel 最有代表性**的一条。

## Project Introduction

"长上下文下解码每步的时间几乎线性增长，注意力占了 80%。原因是每层可并行的块太少、
每块要串行走完整段上下文。我把**上下文维切开**（两阶段归约），斜率降了约 88%，**不改任何数值判据**。"

## Architecture Explanation

stage-1 每片算局部 `m / l / acc` 写进工作区；stage-2 统一 `max` 后加权归约。
**不用跨块原子合并**——原子累加无法保序，结果不可复现。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 切哪一维 | **上下文维** | 再细分头维：块数翻倍但每块仍要串行走完上下文 |
| 归约方式 | **两阶段** | 保序、可复现 |
| 片数为 1 时是否走单趟 | **做不到**：宿主拿不到长度 | 网格恒为上限 + 每块自查有效片数 |
| 工作区尺寸 | 按动态形状 **`.max`** | 按当前形状会偏小并越界 |
| 旧单趟实现 | **永久保留** | A/B 对照入口 + 工作区不可用时的兜底 |

## Technical Challenges

1. **宿主可见性**：不能在宿主侧判断"要不要分片"（长度在设备上，且循环内禁止同步）。
2. **测量协议**：跨 session 不可比；必须同二进制 + 同轮交替 + 报分位。
3. **回归与观测项的区分**：短上下文 +0.9% 左右的小回归，经作者决定作为观测项、**不设判据**。

## Trade-offs

- 并行换来斜率大降，代价是短上下文多一次归并发射（约 1~2%）。
- 保留旧实现换来 A/B 与兜底，代价是库里多一份 kernel。

## Interview Questions

### Level 1

Q：做了什么？　A：把解码注意力的上下文维切开并行，用两阶段归约合并。

### Level 2

Q：为什么不切头维？　A：块数翻倍但每块仍要串行走完上下文，延迟不减。

### Level 3

Q：为什么不用原子合并？　A：无法保序 → 结果不可复现，与项目的可复现判据冲突。

### Level 4

Q：短上下文为什么变慢？　A：多一次归并发射；因为宿主判不出长度，只能"多发一次、空片直接返回"。

### Level 5

Q：怎么证明没放松判据？　A：数值判据一个字没改；新旧差值 3.6e-07 / 1.5e-06，是 float32 累加顺序的量级。

## Follow-up Questions

- 怎么测量？（同二进制 A/B + 同轮交替 + 报中位数与分位；本机拿不到逐 kernel 时间线）
- 还有什么可做？（块内改 "warp-per-position"，但必须先有测量支撑）
