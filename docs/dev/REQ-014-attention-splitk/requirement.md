# Requirement

> **性质**：历史需求回填（2026-10-01）。内容从下列来源抽取，**未新增任何当时的决定**。
> **来源**：`docs/future_iterations.md` §2.2；`docs/future_iterations_development_plan.md` §12.2。
> **判据的另一半**：同开发计划 §12.6（验收判据）；测试计划 §11。
> **数字与结论**：不在本文重复。
> **状态**：已交付（真机验证通过）。

## Problem

实测显示：上下文变长时，解码每步的时间几乎线性增长，注意力在长上下文下占每步的绝大部分；
机制是每层可并行的块数远少于硬件的并行度，每块要串行走完整个上下文，
有效带宽只有峰值的一小部分。

## Goal

把解码阶段注意力的**上下文维**切开并行（分片 + 两阶段归约），
**在不放松任何数值判据的前提下**降低长上下文每步的边际成本。

## Scope

### Included

- 两种精度各一条分片 kernel。
- 暂存显存的契约（按动态形状的**上界**申请，不是按当前形状）。
- 分片策略：切成纯函数、可离线单测。
- 端到端与 kernel 级两个层级的性能对照。

### Excluded

- **不扩批量**：把批量和上下文维混在一起会让性能读数无法归因。
- 不改分页注意力的预填充阶段（那是独立条目）。
- 不做低精度 KV 缓存。
- 不做 CUDA Graph 捕获下的时间线分析。

## Acceptance Criteria

来源：`docs/future_iterations_development_plan.md` §12.6（7 条，逐条带"凭什么"）。

1. **正确性（主）**：生产路径对 CPU 双精度参考仍满足既有算子口径（相对与绝对界），**本轮不放宽**。
2. **边界覆盖**：MHA / GQA / MQA、批量 > 1、跨多块、上下文长度为 0、带当前 token、
   总长度小于分片数（空分片）——每项都要有用例。
3. **语义不变（硬）**：解码一致性用例通过，且 8 token 贪心输出与既有基线**逐 token 一致**。
4. **新旧差异（诊断，非判据）**：打印最大绝对/相对差；先量"与正确性无关的差异"
   （浮点累加顺序不同）再谈阈值。
5. **性能**：长上下文档的**每步斜率**相对基线至少降 40%；
   短上下文档的退化改为**观测项、不设判据**（"不超过同 session 漂移"这个说法被否证：
   "漂移"有多种定义、曾议的 2% 无出处）。
6. **缓存安全**：版本号 bump 后第一次全部过期重建、第二次命中缓存。
7. **无回归**：沙箱全量 0 失败；真机全量仍只有那个"按设计的红"。

## Constraints

- 数值判据不许放松；任何"看起来变差"的读数，先查，再考虑是否量的是无关差异。
- 暂存显存必须按动态维的**上界**申请——按当前形状申请会偏小并越界。
- 分片切法与暂存布局**只能有一份实现**，避免两处各自演进后静默错位。
- 片数由设备端按各序列的上下文长度自行推导，不能在主机侧判定（主机拿不到该值）。

## 历史演进（抽取时保留）

- 第 5 条的后半句原为"短上下文退化不超过同 session 漂移"，后**作废**：
  "漂移"有歧义、曾议的 2% 无出处 → 经作者决定改为**观测项**。这是"阈值必须有出处"的又一实例。
- 本需求在立项时修订过范围：原文含"支持解码阶段的批处理优化"，
  但核查发现 kernel 本就支持批量，把批量卡在 1 的是运行时 → 该句作废，本条只做上下文维。
