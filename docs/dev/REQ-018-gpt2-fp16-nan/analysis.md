## Current Architecture

复现路径上的结构：

```text
权重（FP32 源）→ 语言模型原生建图（常量按"整网倾向精度"建）
      ↓
两层引擎：prefill（整段前向，导出每层 K/V）/ decode（单 token，读分页 cache）
      ↓
运行时：查询引擎声明的边界精度 → 分配缓冲 → 采样
      ↓
诊断仪器：第 0 层的 4 个中途张量（可选导出）+ 逐层 K/V 扫描
```

关键结构事实：

- 弱类型网络：是否用 FP16 由 TensorRT 按 flag 与 tactic 决定，**图层没有强制逐算子类型**。
- 归一化层已经显式设成 FP32 计算精度（这是上一轮定位的产物，已被证明不是根因但保留）。
- 诊断输出是一个**开关**（默认关），打开会改变网络的 I/O 契约——这本身也曾造成过真机 6 条红
  （`docs/TROUBLESHOOTING.md` + TS-019）。

## Module Structure

| 模块 | 与本题的关系 |
|---|---|
| 语言模型构建器 | 建图处；中间张量的导出点都在这里 |
| 构建配置 | 精度档位与诊断开关 |
| 运行时 | 按引擎声明的精度分配缓冲；FP16 下 K/V 与 logits 的声明精度与配置不同（已固化处理） |
| 诊断用例 | 打印各输出是否 NaN、逐层 K/V 的幅值 |
| 复现用例 | FP16 贪心 8 token 与参考对比（当前按设计红） |

## Data Flow

诊断数据流（当前只覆盖第 0 层）：

```text
prompt → prefill 前向
   ├─ 每层 K/V 输出 → 逐层扫 NaN/Inf（能定位"从第几层开始"）
   └─ 第 0 层中途张量（注意力残差 / MLP 残差 / c_fc / GELU）→ 判断 MLP 还是注意力
      ↓
末行 logits 统计（max / mean / 是否 NaN）
```

## Runtime Flow

- 每次真机诊断需要：重建 FP16 引擎（分钟级）→ 跑一次 prefill → 读回诊断张量 → 人工比对。
- 引擎缓存按构建指纹复用；改图 / 改开关会触发重建（属预期）。

## Existing Limitation

### 已经否证的方向（不要重查）

| 方向 | 否证依据 |
|---|---|
| LayerNorm 计算精度 | 显式设 FP32 后 NaN 依旧、位置不变 |
| MLP 前半段（`c_fc` / GELU） | 两个切点都干净，而同一层的残差输出是 NaN |
| 注意力输出 | 第 0 层注意力残差干净 |
| 残差膨胀到 FP16 溢出 | 幅值全在几十以内，距 65504 差几个数量级 |
| "NaN 层在漂移" | 是**观测缺口**：中途张量只导出了第 0 层，看不到后面 |

### 尚未回答的问题

1. **最早出现非有限值的确切位置**：现有仪器只能给"第几层的 K/V"，给不出"层内哪个算子"。
2. **是否与 tactic 选择相关**：同事不同构建下 NaN 层不同，指向"某个算子在 FP16 下的数值行为
   随 tactic 变化"。本机（WSL2）拿不到 kernel 级时间线，但**图层级的 tactic 信息可读**
   （引擎检查器），这条路还没走过。
3. **是否是"具体算子的输入极端值"**：幅值整体不大，但**局部最大值**没有被记录过
   （现在只记了 K/V 的 max|v| 与前 3 层的幅值）。
4. **FP16 引擎里哪些张量真的以 FP16 执行**：弱类型网络下这是 TRT 决定的，属于**可查询**的事实，
   但从未被系统记录过（只在边界张量上查过）。

### 已知的观测陷阱（写下来避免重蹈）

- **仪器覆盖不足时不要把"观测缺口"当成现象**（TS-018.1 的方法教训 1）。
- **每轮只改一个变量**（TS-018.1 的方法教训 2）——同时加两个切点会分不清归因。

## Extension Point

- **诊断面扩展**：把中途张量的导出从"只有第 0 层"扩到全部层（或按需的前 N 层），
  是回答"最早在哪一层哪个算子"的最短路径。改动集中在构建器的导出点。
- **精度事实的读取**：引擎检查器能读出**逐层**的实际计算精度与 tactic 选择，
  这是当前唯一不需要 GPU 时间线就能拿到的"算子在 FP16 下怎么执行"的事实来源。
- **二分手段**：对可疑算子显式设计算精度，是"逐算子二分"的现成手段（归一化上已经用过一次）。

### Overview

B2 分两步走，且**第一步没做完就不许进第二步**：

| 步骤 | 内容 | 预算判定 |
|---|---|---|
| **B1' 补齐观测** | 把"最早出现非有限值的层/算子"钉死 | 属于诊断，不算修复预算 |
| **B2 最小修复** | 针对钉死的算子做显式精度 / 数值稳定化处理 | 见下方逐路线预算 |

### Architecture

当前架构不改动。诊断侧只增加"观测面"：

```text
prefill 前向
   ├─ 逐层 K/V（已有）→ 定位层
   ├─ 新增：逐层中途张量（残差 / GELU 等）→ 定位层内位置
   └─ 新增：从引擎检查器读出该层各算子的实际计算精度与 tactic
      ↓
对照 FP32 引擎的同一份读数
```

### Module Design

| Module | Responsibility | Dependency |
|---|---|---|
| 诊断导出点（构建器） | 把可疑层的中途张量挂成网络输出 | 现有诊断开关机制（会改 I/O 契约） |
| 诊断用例 | 跑固定 prompt、读回、按层打印"是否非有限 + 幅值" | 现有诊断用例 |
| 引擎检查器读数 | 读出逐层精度与 tactic，作为"算子在 FP16 下怎么执行"的事实 | 逐层精度开关 |
| 修复面 | 对钉死的算子显式指定计算精度或等价处理 | 归一化处已有先例 |

### Data Structure

```text
LayerProbe {                  // 每条 = 一次诊断读数
    int32_t layer;
    const char* tensor;       // 残差 / GELU / K / V ...
    bool has_non_finite;
    float max_abs;
}
```

要点：**必须同时记"是否非有限"与"幅值"**——只看前者分不清"突变"与"逐步膨胀"，
这正是上一轮走过的弯路。

### Runtime Flow

```text
重建 FP16 引擎（开诊断导出）
   ↓ 固定 prompt、固定 seed
跑一次 prefill
   ↓
读回逐层读数 → 找"第一个非有限值" → 定位到层内算子
   ↓
对候选算子显式设 FP32 → 只改这一处 → 重建 → 复跑
   ↓
非有限值消失 且 与 FP32 基线逐 token 一致 → 进 B3
```

### Resource Lifecycle

| 资源 | 变化 |
|---|---|
| 诊断输出的缓冲 | 每次诊断按需分配，用完释放；**不进产品路径**（默认关） |
| 引擎缓存 | 开 / 关诊断会改变网络 → 指纹不同 → 各自独立缓存，避免互相判过期 |
| 运行时缓冲 | 不变 |

### Performance Consideration

- 本题**不追求性能**。修复的目标是"默认精度可用"。
- 若最终方案是"部分算子保 FP32"，代价是每层多几次类型转换，**必须如实报告**，
  且不能声称"没有代价"。
- 本机无 Tensor Core：即使修好 FP16，收益也主要是"显存减半 / 带宽减半"，
  性能对照要按带宽口径讲，不要按算力口径讲。

### Trade-off

#### D1 修复路线（来自 `docs/future_iterations.md` §1.4，按成本从低到高）

| 路线 | 说明 | 预估改动面 | 预算判定 |
|---|---|---|---|
| **① 关键算子显式保 FP32** | 残差相加、Softmax 等设 FP32 计算精度，FP16 只用于矩阵乘 | 1 个文件、约几十行 | **可能刚好在预算内**（须实测后判定） |
| ② 逐算子二分 | 把诊断切点扩到前若干层，逐点排除 | 1~2 个文件，改动量取决于层数 | 大概率**超 100 行**（导出点是按层铺开的） |
| ③ 激活缩放 | 在图上引入缩放因子 | 多处改动 + 需要新的数值论证 | **明确超出 Bugfix 预算** |

#### D2 预算超限时怎么办

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 停在诊断结论 | 输出"是哪一层哪个算子 + 为什么"，不改产品代码 | 成本最低、结论可复核；但默认精度仍不可用 |
| **B. Bugfix → Feature Decision（推荐流程）** | 由作者决定是否立为 Feature，走完整设计流程 | 合规（技能明确禁止自动转换）；但要走完整套流程 |

**决策：由作者拍板**。本节不预设结论。

#### D3 观测扩展的方式

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 全部层都导出中途张量 | 一次看全 | I/O 数量翻很多倍，引擎体积与构建时间上升；且"漏绑输出"是踩过的坑 |
| **B. 按需导出（推荐）** | 只导可疑层，分批做 | 每轮要一次真机往返；但风险小、归因清楚 |

### Risk

| 风险 | 影响 | 缓解 |
|---|---|---|
| 诊断输出漏绑 | 真机多条用例转红（已发生过一次） | 诊断始终走独立引擎路径 + 默认关；复跑全量确认 |
| 每轮改多个变量 | 归因不清 | 沿用"每轮只改一个变量"的既有教训 |
| 修好后 FP32 路径被改坏 | 回归 | B3 必须跑全量，不只看目标用例 |
| 把阈值放宽当成修复 | 掩盖真问题 | 本条不新增放宽的阈值；判据是"与 FP32 逐 token 一致" |
