# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"优化采样：先把基线量出来（Top-P 相对贪心高两个数量级），再用'保留排序 + 行内并行'的方案把
每步采样开销压下去——**语义一个字不改**。"

## Architecture Explanation

每行一个 block：先扫描求分母，再在寄存器里维护候选（阈值迭代收紧），块内归并出候选集，
最后只对候选排序并走原有采样数学。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 接口形态 | **不变**（只改工作区返回值） | 调用方只查询大小 |
| 隐式契约 | **显式化**（相同值取小下标） | 否则新实现会出现"偶发不同 token" |
| 阈值来源 | **先测基线** | 性能判据不能拍脑袋 |
| A/B 方式 | **同二进制 + 同轮交替** | 跨 session 的差值不可比 |

## Technical Challenges

1. **并列语义**：既有实现隐式依赖"相同 logits 取小下标"，换实现必须显式保证。
2. **测量判别力**：本平台这类测量的判别下限约 ±400~600 µs——低于它的差异只能写"无显著差异"。
3. **撤出未达标实现**：Top-K 快速路径正确但更慢，按纪律撤出生产路径，而不是留着"看起来更快"。

## Trade-offs

- 只优化 Top-P → 换来确定的 4/4 达标，代价是 Top-K 的快速路径暂时空着。
- 保留旧单趟实现 → 换来永久 A/B 入口与兜底，代价是库里多一份代码。

## Interview Questions

### Level 1

Q：采样器优化了什么？　A：Top-P 的行内数学块内并行；Top-K 尝试了部分选择但未达标、已撤出。

### Level 2

Q：为什么要先测基线？　A：否则"要不要换实现"和"达标线定多少"都是猜的。

### Level 3

Q：怎么保证语义不变？　A：采样数学与随机数消费逐条对齐；并列取小下标显式保证；既有用例不改判据全过。

### Level 4

Q：性能怎么判？　A：同二进制 A/B、同轮交替、报中位数与四分位；低于判别下限只能写"无显著差异"。

### Level 5

Q：有做完了却不达标的吗？　A：有——Top-K 快速路径正确但慢 6~9 倍，按纪律撤出生产路径并记录根因。
