# Design

> 本文是 **B2 的候选方案与预算判定**，不是已批准的实现方案。
> 按 Bugfix 规则：根因未定位前不得改代码；预算超限时必须停下来做
> **Bugfix → Feature Decision**，禁止自动转换。

## Overview

B2 分两步走，且**第一步没做完就不许进第二步**：

| 步骤 | 内容 | 预算判定 |
|---|---|---|
| **B1' 补齐观测** | 把"最早出现非有限值的层/算子"钉死 | 属于诊断，不算修复预算 |
| **B2 最小修复** | 针对钉死的算子做显式精度 / 数值稳定化处理 | 见下方逐路线预算 |

## Architecture

当前架构不改动。诊断侧只增加"观测面"：

```text
prefill 前向
   ├─ 逐层 K/V（已有）→ 定位层
   ├─ 新增：逐层中途张量（残差 / GELU 等）→ 定位层内位置
   └─ 新增：从引擎检查器读出该层各算子的实际计算精度与 tactic
      ↓
对照 FP32 引擎的同一份读数
```

## Module Design

| Module | Responsibility | Dependency |
|---|---|---|
| 诊断导出点（构建器） | 把可疑层的中途张量挂成网络输出 | 现有诊断开关机制（会改 I/O 契约） |
| 诊断用例 | 跑固定 prompt、读回、按层打印"是否非有限 + 幅值" | 现有诊断用例 |
| 引擎检查器读数 | 读出逐层精度与 tactic，作为"算子在 FP16 下怎么执行"的事实 | 逐层精度开关 |
| 修复面 | 对钉死的算子显式指定计算精度或等价处理 | 归一化处已有先例 |

## Data Structure

```text
LayerProbe {                  // 每条 = 一次诊断读数
    int32_t layer;
    const char* tensor;       // 残差 / GELU / K / V ...
    bool has_non_finite;
    float max_abs;
}
```

要点：**必须同时记"是否非有限"与"幅值"**——只看前者分不清"突变"与"逐步膨胀"，
这正是上一轮走过的弯路。

## Runtime Flow

```text
重建 FP16 引擎（开诊断导出）
   ↓ 固定 prompt、固定 seed
跑一次 prefill
   ↓
读回逐层读数 → 找"第一个非有限值" → 定位到层内算子
   ↓
对候选算子显式设 FP32 → 只改这一处 → 重建 → 复跑
   ↓
非有限值消失 且 与 FP32 基线逐 token 一致 → 进 B3
```

## Resource Lifecycle

| 资源 | 变化 |
|---|---|
| 诊断输出的缓冲 | 每次诊断按需分配，用完释放；**不进产品路径**（默认关） |
| 引擎缓存 | 开 / 关诊断会改变网络 → 指纹不同 → 各自独立缓存，避免互相判过期 |
| 运行时缓冲 | 不变 |

## Performance Consideration

- 本题**不追求性能**。修复的目标是"默认精度可用"。
- 若最终方案是"部分算子保 FP32"，代价是每层多几次类型转换，**必须如实报告**，
  且不能声称"没有代价"。
- 本机无 Tensor Core：即使修好 FP16，收益也主要是"显存减半 / 带宽减半"，
  性能对照要按带宽口径讲，不要按算力口径讲。

## Trade-off

### D1 修复路线（来自 `docs/future_iterations.md` §1.4，按成本从低到高）

| 路线 | 说明 | 预估改动面 | 预算判定 |
|---|---|---|---|
| **① 关键算子显式保 FP32** | 残差相加、Softmax 等设 FP32 计算精度，FP16 只用于矩阵乘 | 1 个文件、约几十行 | **可能刚好在预算内**（须实测后判定） |
| ② 逐算子二分 | 把诊断切点扩到前若干层，逐点排除 | 1~2 个文件，改动量取决于层数 | 大概率**超 100 行**（导出点是按层铺开的） |
| ③ 激活缩放 | 在图上引入缩放因子 | 多处改动 + 需要新的数值论证 | **明确超出 Bugfix 预算** |

### D2 预算超限时怎么办

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 停在诊断结论 | 输出"是哪一层哪个算子 + 为什么"，不改产品代码 | 成本最低、结论可复核；但默认精度仍不可用 |
| **B. Bugfix → Feature Decision（推荐流程）** | 由作者决定是否立为 Feature，走完整设计流程 | 合规（技能明确禁止自动转换）；但要走完整套流程 |

**决策：由作者拍板**。本文件不预设结论。

### D3 观测扩展的方式

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 全部层都导出中途张量 | 一次看全 | I/O 数量翻很多倍，引擎体积与构建时间上升；且"漏绑输出"是踩过的坑 |
| **B. 按需导出（推荐）** | 只导可疑层，分批做 | 每轮要一次真机往返；但风险小、归因清楚 |

## Risk

| 风险 | 影响 | 缓解 |
|---|---|---|
| 诊断输出漏绑 | 真机多条用例转红（已发生过一次） | 诊断始终走独立引擎路径 + 默认关；复跑全量确认 |
| 每轮改多个变量 | 归因不清 | 沿用"每轮只改一个变量"的既有教训 |
| 修好后 FP32 路径被改坏 | 回归 | B3 必须跑全量，不只看目标用例 |
| 把阈值放宽当成修复 | 掩盖真问题 | 本条不新增放宽的阈值；判据是"与 FP32 逐 token 一致" |
