## Project Introduction

"从零搭一个多模态推理框架的第一阶段：先把构建、依赖与公共基础设施做出来，让后面所有模型都能接进来。"

## Architecture Explanation

分层：`include/`（接口）/ `src/`（实现）/ `tests/`（单一测试目标）/ `third_party/`（源码嵌入依赖）。
上层唯一的扩展点是"注册表 + 构建器抽象"。

## Key Decisions

| 决策 | 选择 | 一句话理由 |
|---|---|---|
| 库形态 | **静态库** | 便于嵌入与分发，不受宿主环境影响 |
| 依赖接入 | **源码嵌入 / 静态** | 与"换机器要能重建"的项目约束一致 |
| 模型分发 | **注册表 + 抽象接口** | 新增模型不改构建入口 |

## Technical Challenges

**"什么才算通过"**：初版判据只看"文件/代码存在"，于是"只声明未实现"的方法也被算过，掩盖了真缺口。
改成"每条判据必须写明验证方式与判定标准"之后才堵住。

## Trade-offs

- 静态库换来了分发简单，代价是二进制体积。
- 源码嵌入依赖换来可重建，代价是首次编译时间长。

## Interview Questions

### Level 1

Q：为什么用静态库？　A：分发与重建简单，不依赖宿主环境。

### Level 2

Q：第三方依赖怎么接的？　A：源码嵌入，分词库只编静态、关掉非必要功能（可执行判据核对产物）。

### Level 3

Q：怎么保证加点新模型不用改构建代码？　A：注册表 + 构建器抽象，注册一个子类即可；并用测试锁住"新增模型无需改 Builder 类"。

### Level 4

Q：这一阶段最容易出错的地方？　A：判据写成"存在即通过"——它会把未实现的能力算成已完成。

### Level 5

Q：如果重做，你会改什么？　A：一开始就要"可执行判据"，不要等发现缺口才补。
