## Problem

项目要在同一仓库里同时承载视觉与语言两条推理路径，但此前是两套各自为政的示例工程：
没有统一的构建骨架、依赖接入方式不一致、缺少公共基础设施抽象，也没有可复用的测试基建。

## Goal

搭出一个**可编译、可测试的骨架**，作为后续所有阶段的公共底座：目录与构建系统、第三方依赖接入、
基础设施（工具/日志/错误检查/内存与计时）、引擎构建的通用化骨架、基础单元测试。

## Scope

### Included

- 目录与 CMake 骨架；根构建接入与验证。
- 第三方依赖接入（SentencePiece 以**静态库**方式嵌入；safetensors 解析）。
- 基础设施：工具函数、日志、CUDA 错误检查、设备/固定内存缓冲、计时器。
- 引擎构建通用化骨架：引擎封装、构建入口、模型注册表、构建器抽象、模型配置解析。
- 基础单元测试与统一的测试目标。

### Excluded

- 任何真实模型构建器。
- 任何自定义 Plugin（归一化 / 旋转位置编码 / 分页注意力）。
- 采样器 CUDA kernel。
- Runner 的自回归循环。
- INT8 校准、内存池化、Profiler 高级功能。

## Acceptance Criteria

来源：`docs/phase0_development_plan.md` §4（每条都写了"验证方式 + 判定标准"）。

1. 根目录 CMake 配置成功（给定配置命令）。
2. 库目标编译成功（构建命令返回 0）。
3. 单元测试全部通过（`ctest`，判据为 **0 failed**；GPU 用例跳过不计失败）。
4. SentencePiece 只产出静态库且非必要功能全部关闭。
5. 存取库能读取真实文件的 header 与张量元数据（不接受"文件不存在返回 false"这类负向用例充数）。
6. 引擎构建入口可扩展：**新增模型无需修改 Builder 类**。
7. optimization profile 能力可用（Phase 0 遗漏、Phase 1.5 补齐的新增判据）。
8. ~~旧模块仍可构建~~ **已失效**（Phase 5 删除旧模块后无法再验证）。

## Constraints

- **判据写法（本阶段确立并沿用至今）**：不接受"文件存在 / 代码已写"作为通过依据；
  每条判据必须写明"用什么命令或用例验证 + 判定标准"。
  触发这条纪律的原因是：初版判据让"只声明未定义"的方法也算通过，而动态 shape 能力实际不可用。
- 依赖必须可离线接入；嵌入的第三方库要能控制其构建产物形态。
