# Analysis

> **性质**：历史分析回填（2026-10-01）。来源：本目录 `phase0_development_plan.md` §1 / §2 / §3 与
> `phase0_code_review_plan.md`。技能的 `analysis.md` 指"当前系统实现"；对历史条目即**开工时**的现状。

## Current Architecture

开工前不存在统一骨架：仓库里是**两套各自为政的示例工程**，各有自己的构建脚本与依赖接入方式；
新框架 `mini_trt_llm/` 只有空目录，没有库目标、没有公共基础设施。因此"配置 + 权重 → 引擎 → 推理"
这条链路当时**根本不存在**。

## Data Flow

目标链路（当时规划、后由后续阶段逐步实现）：

```text
config.json → 配置解析 → 注册表分发 → 模型构建器 → 权重常量 → 网络 → 引擎 → 推理
```

开工时这条链路的每一环都缺：没有配置解析、没有注册表、没有构建器抽象、没有权重加载。

## Relevant Modules

| 模块 | 开工时状态 |
|---|---|
| 构建系统 | 无统一目标；`mini_trt_llm/` 未接入根构建 |
| 第三方依赖 | 未接入（分词库、张量文件解析库都还没有） |
| 基础设施 | 缺错误检查宏、日志、文件 IO、计时、显存/固定内存缓冲 |
| 引擎骨架 | 缺精度枚举、引擎封装、构建入口、模型配置、权重加载、注册表与构建器抽象 |
| 测试 | 无测试目标、无测试基建 |

## Existing Limitations

1. 没有任何可复用的公共底座，后续阶段会被迫各自重复实现。
2. 依赖接入方式不统一，换机器无法按同一套方式重建。
3. 没有测试基建 → 后续所有能力都缺少自动化验证的落脚点。

## Extension Points

- **各模块子目录已在开工前建好**，是后续所有代码的落点。
- **注册表 + 构建器抽象**：是后续所有模型（语言 / 视觉）的接入点，新增模型只需注册一个子类。
- **引擎封装与构建入口**：是"两条模型来源（原生 / 外部图）"共同的上层接口。
