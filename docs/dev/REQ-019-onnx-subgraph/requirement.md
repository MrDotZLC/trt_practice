## Problem

1. **外部图（ONNX）路径当前只是"能跑"，不是"可替换"**：它把整张图直接交给 TensorRT 解析，
   自研算子（归一化 / 旋转位置编码 / 分页注意力）在这条路上**没有任何使用者**。
   同一个模型因此有两条实现路径：一条用手写算子，一条全部交给原生层。
2. **识别只到"计数"级别**：现在的识别是"数一数图里有几个某类算子、和一条固定基线比一比"，
   **不做拓扑级识别**。计数相同但连接方式不同是识别不出来的——一旦图变了，
   "看起来没变"的假安全感比没有识别更危险。
3. **"替换值不值得做"没有依据**：外部图与原生 prefill 的两次性能测量**方向相反**
   （一次外部图慢约 22%、一次快约 24%），量级小于本平台的构建间噪声。
   在拿到可复现对照之前，任何"替换能提速"的说法都是猜的。
4. **两条路的输入契约不一致**：外部图只有单一输入且元素类型与原生路不同，也缺位置编码输入，
   因此**接不进统一的运行时**；这既是可替换性的前提，也是两条路能对拍的前提。

## Goal

让外部图路径支持**拓扑级子图识别**与**子图替换**（替换成本项目的算子实现），
替换前后数值一致且引擎可用；并且**先有可复现的性能依据**再决定是否推进。

## Scope

### Included

- 前置测量：外部图与原生实现的可复现对照（≥3 次构建 / ≥20 次推理，报中位数与极差）。
- 拓扑级识别：从"计数"升级到"能区分连接方式不同"，并保留现有护栏。
- 子图替换的实现路线选型与落地。
- 自定义算子的导出方式（让外部图里出现本项目算子）。
- 替换前后的一致性判据 + 引擎可用性（构建 / 序列化 / 反序列化 / 推理）。
- 两条路输入契约的统一（至少到"同一套调用方式"）。

### Excluded

- 为外部图新增自研算子（先只替换到**已有**算子实现上；新算子按需另立）。
- 量化融合与低精度替换（那是 `REQ-017-llm-int8-quant` 的范围）。
- 多模型 / 多框架支持；CUDA Graph；服务化。
- "为替换而替换"：若测量表明没有收益，结论就是不做（见设计阶段的 D1）。

## Acceptance Criteria

1. **前置有依据**：PF-7 的对照结论可复现（报构建次数、推理次数、中位数与极差），
   且据此能回答"为什么要替换"。
2. **识别到拓扑级**：能识别并拒绝"计数相同、连接不同"的图；现有算子分布基线护栏保留。
3. **替换可跑**：替换后的引擎能构建、序列化、反序列化并推理。
4. **数值一致**：替换前后在同一输入上的差异落在**有出处**的判据内（不许新造无来源阈值）。
5. **契约统一**：两条路的输入 / 输出契约一致，同一套调用方式可直接切换。
6. **不回归**：现有沙箱用例全绿；真机既有用例不出现新红。

## Constraints

- 硬件：GTX 1660 Ti（sm_75、单卡、无 Tensor Core），6 GB 显存。
- 外部图资产（约 650 MB）不在版本控制内，需按项目既有方式重建。
- 识别脚本依赖 Python 侧的图解析库；缺环境时按既有约定"跳过并打印"，缺资产则判失败。
- 沙箱无 GPU：引擎构建与数值 / 性能验收只能在真机完成（需批准）。
- 阈值纪律：`AGENTS.md` §7。
- **设备纪律**：一旦检测到当前设备不是本项目的**目标真机**（硬件与工具链基线见项目级指南 §1），
  必须**立即确认该设备是否具备真机测试能力**，并把结论写进当轮回复与本条目的 `STATE.md`；
  不得自行假设"没有就跳过"，也不得把"未验证"写成"已通过"。
