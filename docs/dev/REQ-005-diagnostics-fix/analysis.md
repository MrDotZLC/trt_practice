# Analysis

> **性质**：历史分析回填（2026-10-01）。来源：本目录 `phase2_supplement_plan.md` §0 / §2。

## Current Architecture

上一阶段为定位数值问题，在图上挂了**诊断用的中途输出**；它们**无条件进入网络 I/O 契约**，
而消费方是按名字绑定输出的——没人绑它们，`enqueue` 直接失败。同时"沙箱内 CUDA 不可用"
被表现为**跳过**而不是失败，形成"假绿滑梯"。

## Data Flow

```text
建图：4 个中途张量被无条件标记为网络输出
   ↓
绑定：消费方只绑它知道的输出（生产路径不绑诊断输出）
   ↓
enqueue：运行时要求每个输出都有地址 → 失败，而且报的是那个诊断张量的名字
```

## Relevant Modules

| 模块 | 开工时状态 |
|---|---|
| 构建配置 → 构建选项 | 缺"诊断开关"这一层 |
| 建图 | 诊断输出按"切面 + 层号"条件挂载，**没有开关** |
| 引擎缓存 | 诊断路径与生产路径共用命名 → 互相判过期 |
| 测试基建 | "无设备"与"功能失败"没有分开表达 |

## Existing Limitations

1. 诊断输出污染生产契约 → 真机多条用例直接失败。
2. 环境不可用被当成跳过 → 覆盖损失不可见。
3. 两条路径共用引擎缓存 → 来回重建。

## Extension Points

- **构建选项**：项目所有构建期参数都走"配置 → 构建选项"这条路径，诊断开关是它的新成员。
- **独立引擎路径**：是"诊断路径不影响生产"的通用做法，后续测量类工具也照此办理。
