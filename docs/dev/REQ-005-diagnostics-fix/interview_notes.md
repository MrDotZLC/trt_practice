# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"一次典型的'诊断代码伤了产品'的事故修复：为了查数值问题挂的中间输出进了网络契约，
把真机用例打挂；同时沙箱里的环境问题被伪装成'跳过'。两件一起修。"

## Architecture Explanation

关键区分：**诊断输出不是调试开关，而是 I/O 契约开关**——多一个输出，每个消费方都必须绑定。
所以它默认关、且走**独立引擎路径**，避免与生产路径抢缓存。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 诊断输出默认值 | **关** | 默认打开等于把契约变更推给每个调用方 |
| 两路径是否共用引擎缓存 | **独立命名** | 共用会互相判过期、来回重建 |
| 环境不可用怎么表达 | **显式跳过 + 打印探测原因** | 功能失败必须判红，不能被"跳过"掩盖 |

## Technical Challenges

**"跳过"是 CI 里最危险的状态**：它被 `ctest` 记作 Passed，于是覆盖损失不可见。
这一批次把"无设备"与"功能失败"分开，并用一条对照判据（FP16 复现器应回到"按设计红"）证明
开关真的穿透到了底。

## Trade-offs

- 诊断要独立建引擎（分钟级）→ 换来生产路径零影响。
- 不引入缓存失效机制 → 换来本批次范围可控，代价是留了一个"靠路径隔离"的临时手段。

## Interview Questions

### Level 1

Q：这个修复解决什么？　A：诊断输出污染网络契约导致真机用例失败；以及环境问题伪装成跳过。

### Level 2

Q：为什么默认关？　A：它是契约变更——多出来的输出每个消费方都得绑。

### Level 3

Q：怎么证明开关穿透到底了？　A：9 条用例全绿**且** FP16 复现器回到"NaN → token 全 0"的按设计形态。

### Level 4

Q：为什么两条路径要分开缓存？　A：引擎缓存只按路径名区分，共用会互相判过期、来回重建。

### Level 5

Q：为什么不顺手把缓存失效机制做掉？　A：那属测试基建改造，混进来会让本批次范围失控、归因不清。
