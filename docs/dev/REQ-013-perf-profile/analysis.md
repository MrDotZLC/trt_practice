# Analysis

> **性质**：历史分析回填（2026-10-01）。来源：本目录 `future_iterations_development_plan.md` §11.1 / §11.2。

## Current Architecture

性能结论此前只能靠**单次点值**，跨 session 的数字彼此不可比；"时间花在哪"没有可归因的粒度——
既说不清采样器占比，也说不清注意力占比，更没量过显存分配到底贵不贵。

## Data Flow

```text
一键采集入口（系统级 / kernel 级）→ 报告落文件、控制台只回摘要
        ↓
分桶脚本（含自检）→ 三层时间之和 vs 总时间 → 结论（含偏差与构建态）
```

## Relevant Modules

| 模块 | 开工时状态 |
|---|---|
| 测量协议 | 不存在（只有单次点值） |
| 采集入口 | 不存在 |
| 分桶脚本 | 不存在 |
| 判别下限 | 未测（无从判断"差异是否显著"） |

## Existing Limitations

1. 单次/分段测量与固定开销同量级 → 结论可能是从噪声里读出来的。
2. 没有"同二进制 A/B"的统一做法。
3. 不知道 sampler / attention / 显存分配各占多少 → 优化无从排序。

## Extension Points

- **测量协议**：同 session、同轮交替、报中位数与四分位、先给判别下限——后续所有性能结论都靠它。
- **一键采集**：把"怎么跑剖析"固化下来，不依赖人记得。
- **分桶脚本**：把时间归因到可复核的粒度。
