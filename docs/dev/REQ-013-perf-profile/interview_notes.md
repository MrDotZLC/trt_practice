# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"先解决'能不能信'的问题：建立一个同 session 内可复现的测量方法（含判别下限与报告格式），
再用它回答'时间到底花在哪'——采样器、注意力、显存分配各占多少。"

## Architecture Explanation

两类问题两种测法：**同二进制内的 A/B**（两版编进同一二进制、同轮交替）与**跨构建对照**
（同 session 内多次构建，报极差）。报告必须含形状、构建态、样本量、分位、温度时钟与命令原文。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 能否锁时钟 | **不假设能锁** | 平台不支持；假装锁定会让结论失去依据 |
| 采样器占比是否设阈值 | **不设**，只给观测值与区间 | 它回答"占多少"，不是"达标没有" |
| 两口径冲突时以谁为准 | **隔离计时** | 时间线有采样开销，且本机拿不到 |
| 逐 kernel 分解 | 记为**能力边界** | 本机两条 CLI 路径都拿不到 kernel 数据 |

## Technical Challenges

1. **噪声与信号同量级**：必须先把"判别下限"量出来，否则会把噪声当结论。
2. **"看起来像真故障"的数字**：分层与分解都要自证（三层之和 vs 总时间）。
3. **结论要能复跑**：报告里必须带构建态与温度时钟，否则下次没人能复现。

## Trade-offs

- 不追求逐 kernel 分解 → 换来结论可靠（只用比值与斜率），代价是粒度粗。
- 采集入口不进默认构建 → 换来生产契约不受影响，代价是要显式调用。

## Interview Questions

### Level 1

Q：这份工作产出什么？　A：一套可复现的测量协议 + 一键采集 + 三个问题的答案。

### Level 2

Q：为什么要判别下限？　A：本平台的噪声与固定开销和信号同量级；低于下限的差异不能称为"更快"。

### Level 3

Q：怎么保证两次测量可比？　A：同一 session、同轮交替、同二进制（A/B）；跨构建对照另有一组规则。

### Level 4

Q：分解怎么自证？　A：给出三层时间之和与总时间的偏差，并附命令、形状、样本量与构建态。

### Level 5

Q：测量过程中有没有翻车？　A：有——一次测量把"块间漂移"算进分子分母，导致"判不了"；协议因此加了"配对/交替"要求。
