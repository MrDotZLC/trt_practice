## Problem

性能结论此前只能靠单次点值，跨 session 的数字彼此不可比；同时"时间花在哪"没有可归因的粒度——
既说不清采样器占比，也说不清注意力占比，更没量过显存分配到底贵不贵。

## Goal

建立**同一 session 内可复现**的性能测量方法 + 一键性能采集入口，
并用它把解码阶段的时间分解到**可归因的粒度**，回答三个待决问题：

1. 采样器在整步解码里占多少；
2. 注意力占多少（决定长上下文优化是否值得做）；
3. 显存分配的开销是否足以支撑"替换显存池"这类改动。

## Scope

### Included

- 测量协议：同 session、同二进制、逐轮交替、报中位数与四分位、先给判别下限。
- 一键采集入口（系统级与 kernel 级各一套 target），产物落文件、控制台只回摘要。
- 时间分桶脚本（含自检）。
- 用该协议回答上述三个问题，并回填文档。

### Excluded

- **只导出、不调优**：本条不负责据此做性能优化。
- 不把采集 target 进默认构建；用独立引擎路径，避免改动生产契约。
- 逐 kernel 分解（受本机能力限制，见 Constraints）。

## Acceptance Criteria

来源：`docs/future_iterations_development_plan.md` §11.6（逐条带"凭什么"）。

1. 系统级无头导出可用（报告存在且非空，能在无 GUI 下打出摘要）。
2. kernel 级无头导出：**本机实测不可用** → 记为**已知限制**，而不是"通过"。
3. 同二进制 A/B **可判**：两次交替测量的中位数之差必须超过实测判别下限才算"有差异"。
4. 跨构建对照**可判**：同一 session 内多次构建的中位数极差小于两组中位数之差；否则结论只能是"未定"。
5. 分解**可复核**：三层时间之和与总时间的偏差要写出来；命令、引擎指纹状态、形状、样本量全部给出。
6. 采样器占比给出**观测值**（中位数与区间），**不设阈值**——设阈值会退化成被禁止的判据。
7. 生产路径不受影响（采集入口不进默认构建、逐层精度开关走独立引擎路径）。

## Constraints

- **本机能力边界**：拿不到 GPU 逐 kernel 时间线（两条 CLI 路径都实测失败）。
  逐 kernel 分解记为能力边界，改用"同 session 比值 + 上下文扫描"。
- 跨 session 的数字不可直接比较；这点有实测教训。
- 平台存在判别下限（约几百微秒量级），小于它的差异不得宣称。
- 采集会改变引擎缓存路径，必须与生产路径隔离。
