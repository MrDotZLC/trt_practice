## Problem

1. **一次只服务一个请求**。当前自回归推理运行时按"批量 = 1"设计：整条 decode 循环、结果缓冲、
   K/V 登记都只服务一条序列。多请求只能串行排队，设备利用率低。
2. **decode 是访存受限，却完全没有摊薄**。每生成一个 token 就要把全部权重读一遍显存，
   而参与计算的只有 1 个位置的激活。批量 > 1 时同一份权重只读一次、算多行，这是这一档
   延迟-吞吐曲线里最直接的杠杆。
3. **分页 K/V 的记账能力已经具备，但运行时侧没有调度**。请求何时进入批次、结束后何时归还
   K/V 块、批次成员在运行中如何变化，这些当前没有定义，也没有"跑完 N 轮不泄漏"的保证。

## Goal

让推理运行时能同时服务多条序列，并具备最小的请求调度能力：请求可以进入批次、在批次内各自
推进、结束后释放其 K/V 资源；批量执行的数值结果与"逐条单独执行"一致。

## Scope

### Included

- 批量 > 1 的 prefill 与 decode 路径（同一份权重、同一份 K/V 池、同一批 token 一起前向）。
- 每序列独立的长度记账、位置编码推进与结果收集。
- 每序列独立的 K/V 分页分配与回收。
- 请求级调度：先做静态批（一批请求同进同出），再做运行中增补 / 退出的最小连续批。
- "批量运行 == 逐条单独运行"的数值一致性判据。

### Excluded

- 抢占与换出（显存不足时把某条序列的 K/V 换到主存，或丢弃后重算）。
- prefill 分块（chunked prefill）与 prefill/decode 混批的调度策略。
- 多流并行、CUDA Graph 捕获。
- HTTP / gRPC 服务层；beam search、重复惩罚等新采样语义。
- 跨引擎（多模型）调度与多卡。

## Acceptance Criteria

1. **数值一致性**：同一组请求，批量运行时每条序列的每个 token 与"逐条单独运行"**完全一致**
   （不是"接近"——这是判断"批量路径拼错了没有"的硬判据，逐条单跑本身就是参考实现）。
2. **长度不齐**：批次内各序列已生成长度不同时，位置编码与语境长度逐序列正确。
3. **资源回收**：一条序列结束后其 K/V 块被归还；连续跑 N 轮请求后空闲块数回到初始值。
4. **不回归**：现有沙箱用例全绿；真机既有用例（FP32 端到端、K/V 缓存、插件）不出现新红。
5. **单序列语义不变**：批量为 1 时行为与现状逐 token 相同。

## Constraints

- 硬件：GTX 1660 Ti（sm_75、**无 Tensor Core**）、单卡、6 GB 显存 → 批上限受显存与引擎
  profile 共同约束，不能靠"调大"绕过。
- 解码循环内仍然禁止 H2D / D2H 同步拷贝（项目既有硬约束）。
- 批上限必须落在引擎 profile 声明的范围内，否则引擎直接拒绝执行。
- 沙箱无 GPU：数值与性能验收只能在真机完成（按 `AGENTS.md` §0.3 需先获批准）。
- 判据阈值若需要新增，必须写明出处；不许用"放宽阈值"换取通过（`AGENTS.md` §7）。
