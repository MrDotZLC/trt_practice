## Overview

分三个里程碑，每个都能独立验收：

| 里程碑 | 内容 | 为什么这样切 |
|---|---|---|
| **S1 批量执行** | 一次调用同时跑 N 条序列（prefill + decode），数值与逐条单跑一致 | 先把"批量正确"做扎实；不含调度变量，读数可归因 |
| **S2 资源生命周期** | 元数据缓冲预分配、块回收、跑 N 轮不泄漏 | 没有它，S3 的调度循环会一直重分配，并让"指针是否稳定"变成隐性依赖 |
| **S3 请求级调度** | 请求运行中进入 / 退出（连续批的最小形态） | 服务化的真正入口；也是判据 2 的完整形态所在 |

S1 里再分两小步：先只支持**批内 prompt 等长**，再决定是否支持不等长（见 D2）。
P5 按里程碑分批实现与提交，不把三个里程碑压成一笔。

## Architecture

```text
调用方（多请求）
      ↓
 ┌─────────────────────────────────────────┐
 │ LLMRunner                               │
 │  ├─ 批状态表（每序列：id/状态/长度/参数） │
 │  ├─ 批量形状设置（B, S）与缓冲            │
 │  └─ 采样（per-sequence 参数）             │
 └───────┬─────────────────────┬───────────┘
         ↓                     ↓
   prefill 引擎           decode 引擎
   （[B,S] 前向，          （[B,1] 前向，
    每层导出 K/V）          读分页 cache）
         ↓                     ↓
 ┌─────────────────────────────────────────┐
 │ PagedKVCache（块池 + 每序列块表/长度）    │
 └─────────────────────────────────────────┘
```

## Module Design

| Module | Responsibility | Dependency |
|---|---|---|
| 批状态表（新增，运行时内部） | 每序列的 id、prompt、已生成长度、采样参数、结果缓冲、状态机 | 无 |
| `LLMRunner` | 批量入口；设 `[B,S]` / `[B,1]` 形状；绑定 per-sequence 张量；聚合结果 | 两张引擎、批状态表 |
| `PagedKVCache` | 元数据缓冲**按最大批预分配**；一次导出整批块表 / 长度；块回收 | `BlockAllocator` |
| `BlockAllocator` | 保持不变（free-list 已够用）；但其**失败是抛异常**，调度入口必须先检查后分配（D9） | — |
| 采样器 | 已支持 per-batch 参数指针，无需改 kernel | 现有 sampler |
| `GPT2ModelBuilder` | S1/S2 **不改**；D2 选 B 时才加 mask 输入 | — |

## Data Structure

```text
SequenceState {
    int32_t seq_id;              // 分页 cache 的键，批内唯一
    int32_t prompt_len;          // S1：批内必须相同（D2=A）
    int32_t generated;           // 已生成 token 数
    int32_t context_len;         // prompt_len + generated（仅 host 记账用）
    SamplerParams { top_k, top_p, seed };
    Status { kWaiting, kRunning, kFinished };
}

Batch {
    std::vector<SequenceState> sequences;   // 下标 = 引擎输入的行号
}
```

设备侧每行一个元素：`context_lens[B]`、`position_ids[B]`、`top_k[B]`、`top_p[B]`。
块表 `[B, max_blocks_per_seq]` 沿用现有布局（不足宽度补 0）。
结果缓冲从"一条序列的 `[max_new]`"改成**每序列一段**（D4）。

## Runtime Flow

```text
新请求到达
   ↓
批状态表登记（先查空闲块是否够，再分配块 + 写 prompt）
   ↓
一次批量 prefill：[B,S] → 每层 K/V → 写 cache → 采样 → token_0[B]
   ↓
while 还有序列没结束:
   设形状 [B,1] → decode → 追加 K/V（整步一次）→ 采样 token_{i}[B]
   ↓
某序列命中 EOS / 达到上限 → 标 kFinished → 归还块 → 从批内移除
   ↓
全部结束 → 一次性 D2H → 按序列切分结果
```

## Resource Lifecycle

| 资源 | 何时创建 | 何时释放 |
|---|---|---|
| 分页 cache 与块池 | 运行时构造期（一次） | 析构 |
| 块表 / 长度 / 采样参数设备缓冲 | **构造期按最大批预分配**（S2 的核心改动） | 析构 |
| K/V / logits / token 缓冲 | 首次调用按 `(max_batch, max_seq)` 备好，容量不足才扩 | 析构 |
| 每序列的块 | 请求进入时（**先检查空闲量，避免异常穿透**） | 请求结束（正常 / 出错都要归还） |
| CUDA stream | 沿用默认流，本轮不引入多流 | — |

要点：**解码循环内不分配、不同步**；块归还必须与"从批内移除"同一步完成，否则块池会泄漏。

## Performance Consideration

- **compute**：decode 每步的算子规模随批线性增长；权重读取次数不变 → 批量提高的是
  "每字节显存换来的 token 数"。这是本 feature 的主要收益来源。
- **memory**：真机 GPT-2 下两类占用要分开算。
  * **KV 池**：`num_blocks × block_size × kv_heads × head_size × 元素字节 × 2`（K/V）× 层数；
  64 块、FP32、12 层时约 72 MiB。**它不是瓶颈**。
  * **prefill logits**：`B × S × V × 元素字节`；`S = 512`、FP32 时 B=1 约 98 MiB、B=4 约 393 MiB。
  **这才是随批增长的主要项**，批上限要按它先估。
  * 另有每序列 K/V 输出缓冲（`[B, kv_heads, S, D]`）与其他工作区，P4 一并量。
- **communication**：无（单卡、单流）。
- **测量口径**：沿用项目既有协议——同 session、同二进制 A/B、逐轮交替、报中位数与四分位，
  并先给出判别下限（`docs/PROGRESS.md` §5.13b，本机约 ±400~600 µs）。
  批量收益远大于该下限才值得写结论。**读数必须在关闭常驻诊断的口径下取得（D7）。**

## 不变量（实现时必须显式成立，P6 需要断言覆盖）

1. **池与块表的契约**：引擎把 cache 第 0 维声明为 `ceil(n_positions / block_size)`，这个数同时
   被用作块表宽度；运行时的物理块池**必须 ≥ 块表宽度**。池更大之所以安全，是因为插件用运行期
   偏移在连续的更长缓冲里寻址、且 TRT 不校验输入缓冲容量——这条依据要落成注释与断言（D6）。
2. **profile 归属**：运行时给 prefill / decode 各用一个引擎，且各自**只有一个** profile。
   这条不成立时（例如拿到一个双 profile 的 `kSingle` 引擎）必须在构造期失败，而不是静默用错组（D8）。
3. **循环内零 H2D / D2H**：与现状一致，不因批量改动而放宽。
4. **批内行号一致**：块表第 i 行、`context_lens[i]`、采样参数第 i 项、结果第 i 段必须同源，
   不允许各自维护下标。

## Trade-off

### D1 调度形态

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 静态批（推荐先做）** | 一批请求同进同出 | 实现小、读数干净；但短请求要等长请求，GPU 空转 |
| B. 连续批 | 请求可运行中进入/退出 | 才是服务化的形态；但引入"批内长度不齐 + 每步形状变化"，必须先在 S1/S2 打好底 |

**决策：先 A 后 B**，A 的数值一致性是 B 的前提。

### D2 批内 prompt 长度不等

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 只支持等长批（推荐 S1）** | 不同长度的请求分成不同的批 | **不需要改模型构建器**，最短路径到"批量正确" |
| B. 右填充 + padding mask | 一次吃下不等长批 | 要给 prefill 图加一个 mask 输入 → **改 I/O 契约**、多一个必须绑定的张量 |

**决策：S1 选 A，S3 做 B。** 附加约束：选 B 时不只是"加一个输入"——绑定列表、检视工具、
以及**建图版本号**都要同步改（版本号不进改动会让引擎缓存判定"未过期"而拒绝重建，
静默复用一张没有 mask 的旧图）。
**明确交接**：判据 2（长度不齐）的完整形态落在 S3；若 S3 最终被裁掉，判据 2 必须相应下修并写明原因。

### D3 每序列采样参数

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 全批统一参数 | 一批共用一个 k / p / seed | 最省；但"同一批里有的贪心、有的 top-p"做不到 |
| **B. 每序列参数（推荐）** | 设备端 per-batch 数组 | 采样器接口已经是 per-batch 指针，只需把缓冲从 1 元素扩成 B 元素 |

**决策：B**。成本几乎为零，却把"每请求独立采样策略"这条路留住了。

### D4 结果收集

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 每序列独立 token 缓冲（推荐）** | 每行一个缓冲，结束后整块 D2H | 结果切分简单，长度不齐也能对 |
| B. 一个大矩阵 `[B, max_new]` | 一次拷贝 | 形状整齐时省事，但先结束的序列要填充，语义更容易出错 |

**决策：A**。代价是 B 次拷贝，但都在循环之外一次性发生；换来的是"长度不齐"这条判据不需要
额外的填充语义，也不需要在设备端判断哪一行已经结束。

### D5 与另外两条 feature 的写冲突

本 feature 与 `REQ-017-llm-int8-quant`（改权重精度与 cache 元素宽度）、`REQ-019-onnx-subgraph`
（让 ONNX 路径接入运行时）都要改运行时入口。**三者不能并行改同一个文件**。

**决策：本 feature 先做**（它定义批量契约）→ INT8（在批量契约上扩精度）→ ONNX 路径接入。
理由：契约类的改动放前面，后面两条都是在契约上做加法；反过来会让前两者各自变基一次。
这条需要作者确认——它是 Gate-A 的附带拍板项。

### D6 块池与引擎 cache 张量维度的关系

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 保留"池 ≥ 宽度"的隐含关系，显式化并断言（推荐）** | 引擎声明不变；运行时校验"池 ≥ 块表宽度"，把安全依据写进注释 | 不动模型构建器、不用重建引擎；但安全依赖"插件用运行期偏移寻址"这一实现事实 |
| B. 让引擎把池大小当独立超参声明 | 契约最干净 | 要改模型构建器 + 超参 + 重建引擎，且会改变块表语义，超出本 feature 的范围 |

**决策：A**。理由是它不引入引擎重建，而 B 的收益要等到"池与宽度真的需要解耦"时才兑现。
选 A 必须同时落下两件事：断言 + 注释说明依据（见 §不变量 1），否则这条又变回隐性依赖。

### D7 常驻诊断的去留

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 保持现状常驻 | 不改代码 | 每请求多一次同步 D2H 与逐层 K/V 扫描，真机 `S=512` 约 18 MiB/请求，且随批线性增长 → 污染吞吐读数 |
| **B. 做成开关，P4/P7 一律关闭（推荐）** | 加运行期或编译期开关，默认只在定位数值问题时打开 | 保留诊断能力，同时让性能口径干净 |
| C. 直接删除 | 最干净 | 丢掉已经救过场的能力（FP16 NaN 定位靠它），不划算 |

**决策：B**。并加一条流程要求：P4 的 baseline 与 P7 的对比读数**必须在关闭诊断的口径下**取得；
若两版开关状态不一致，读数作废。

### D8 profile 归属校验

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 不校验，沿用现状 | 零成本 | 拿到双 profile 引擎时静默用错组，表现为"形状设了却不生效"这类难查现象 |
| **B. 构造期校验两个引擎各自的 profile 数（推荐）** | 构造期一次检查，失败即拒绝启动 | 与现有精度校验同风格；把一类隐性错配变成启动期失败 |

**决策：B**。

### D9 块分配失败的语义

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 依赖异常，在调用方 catch | 改动最小 | 分配器对 OOM / 非法 id / 重复释放一律 `throw`；调度循环里异常穿透会带走整个批次 |
| **B. 调度入口"先检查后分配"（推荐）** | 进入批次前先算所需块数与空闲量，不足则该请求排队或拒绝，不进入可能抛异常的路径 | 把失败变成可预期的返回值；不需要改分配器 |

**决策：B**。分配器保持不变；"检查"与"分配"之间不能有其他会改块池的操作。

## Risk

| 风险 | 影响 | 缓解 |
|---|---|---|
| 批内长度不齐导致注意力算错 | 结果静默错 | S1 限定等长；补"批量 == 逐条单跑"对拍用例 |
| 块表宽度与批大小混淆 | 越界写 / 读错行 | 块表宽度由引擎契约固定，批大小只改行数；host 侧镜像补 0 |
| 池被放大到超过引擎声明的 cache 维 | 越界读 / 静默错 | D6 的断言 + §不变量 1 的注释；P4 先量池的实际需求 |
| 元数据缓冲重分配后旧地址仍被使用 | 静默读到旧地址 | S2 按最大批预分配；P6 加"多次调用后指针不变"的断言（当前正确性依赖"每步重绑"，不能继续依赖） |
| **prefill logits 显存被低估** | 批上限设得过大 → 真机 OOM | P4 把 logits 缓冲单列为测量项；批上限写成实测值而不是推算值 |
| 常驻诊断污染性能读数 | 结论失真 | D7：P4/P7 关闭诊断；两版开关状态必须一致 |
| 批量收益被"每步形状变化"吃掉 | 白做 | S1 先测固定批量收益；S3 再单独测调度开销 |
| 图改动但忘记 bump 建图版本号 | 静默复用旧引擎 | D2 的附加约束；改图任务必须把版本号写进 checklist |
