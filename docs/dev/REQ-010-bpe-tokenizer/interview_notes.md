# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"补上框架缺的那一环：文本 ↔ token id。不引入第三方分词库，自己实现字节级 BPE，
并用**独立参考导出的 golden 文件**当标尺——不是'看着差不多'，是**逐 token 全等**。"

## Architecture Explanation

两个数据文件（词表 + 合并规则）在仓库外；载入接口的入参被解释为**目录**（不改基类）；
golden 入库，作为长期标尺。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据文件 | **不入库**，环境/构建变量指向 | 与"大产物不入库"一致；缺文件跳过并打印探测 |
| 载入接口 | **不改基类**，入参=目录 | 避免改动扩散到既有分词器实现 |
| 参考数据 | **golden 入库** | 体积小，它是标尺 |
| 用例层级 | 文本入口等价性**放 host** | 该链路只有一个变量；真机数值已被既有用例覆盖 |

## Technical Challenges

1. **`\uXXXX` 转义**：词表 key 全是这种形式，公共解析器不支持 → 直接读不进来；
   这条前置**计划里没写**，是实现期才发现并补的。
2. **空白语义**：特殊符号只吃**字面空格**，不含制表符与换行——实现时两次踩坑。
3. **字节级回退**：非 ASCII 文本要按字节处理，再按合并规则归并。

## Trade-offs

- 自实现而不引入第三方 → 换来零运行时依赖，代价是边界语义要自己抠干净。
- golden 入库 → 换来标尺可追溯，代价是仓库里多了一个小文件（以及一条自检的成本）。

## Interview Questions

### Level 1

Q：这个分词器做什么？　A：文本 ↔ token id，词表与目标模型完全对齐。

### Level 2

Q：怎么验证它是对的？　A：与独立参考逐 token 全等；参考数据自带来源与哈希。

### Level 3

Q：为什么参考数据要入库？　A：它是**标尺**——标尺必须可追溯、可校验，而不是"某次跑出来的"。

### Level 4

Q：最容易被忽略的语义是什么？　A：空白与前导空格的处理（只吃字面空格；`\uXXXX` 转义要先支持）。

### Level 5

Q：为什么把"文本入口等价性"放在 host 而不是真机？　A：那条链路只有一个变量（分词），
真机数值部分已被既有用例覆盖，再搭一次双引擎不带来新信息。
