# Analysis

> **性质**：历史分析回填（2026-10-01）。来源：本目录 `phase2_development_plan.md` §0 / §1 / §3。

## Current Architecture

算子与测试基建都有了，但**没有任何真实模型跑通**：没有原生建图、没有分页缓存的解码路径、
没有自回归循环。同时项目硬约束要求解码循环内不得出现主机与设备之间的同步拷贝。

## Data Flow

双引擎设计（这一阶段确立）：

```text
配置 + 权重 ─┬─→ 预填充引擎（整段前向，除 logits 外每层导出 K/V）
             └─→ 解码引擎（单 token，读分页缓存，注意力走自研插件）
                        ↑
                  分页 K/V 缓存（块池 + 块表 + 长度）
                        ↑
                  Runner：预填充 → 解码循环 → 采样
```

## Relevant Modules

| 模块 | 开工时状态 |
|---|---|
| 模型构建器 | 只有测试用构建器；没有真实语言模型 |
| 权重转换 | 需要"原生配置 + 权重映射表" |
| 分页 K/V 缓存 | 未落地（块池 / 块表 / 写入内核） |
| Runner | 只有桩 |

## Existing Limitations

1. 没有真实模型 → 数值、契约、性能三类结论都无从谈起。
2. 构建选项不支持"切面"（单引擎 / 仅预填充 / 仅解码），双引擎无法表达。
3. 权重约 150 个张量，转换缓冲的生命周期问题会被**放大**（上一阶段修过同类缺陷）。

## Extension Points

- **权重映射表**：把"运行期名字 → 权重源 key"解耦，是新增模型的关键抽象。
- **构建切面**：预填充 / 解码各一张图，是后续所有性能工作（含 split-K）的基座。
- **K/V 缓存契约**：每层一对独立缓存 + "整步只推一次长度"，后续所有缓存改动都必须遵守。
