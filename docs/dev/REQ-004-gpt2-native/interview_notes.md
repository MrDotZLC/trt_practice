# Interview Notes

> **性质**：历史面试口径回填（2026-10-01）。

## Project Introduction

"让框架第一次真正跑通一个语言模型：原生建图、分页 K/V 缓存、双引擎、自回归循环，
而且解码循环内一次主机-设备同步拷贝都没有。"

## Architecture Explanation

为什么是**双引擎**：预填充是整段前向、注意力用原生算子拼的子图；解码是单 token、注意力走自研插件。
两者结构不同，合成一个引擎会互相拖累。缓存用**每层一对独立张量**，解码时"整步只推进一次长度"。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 引擎切分 | 预填充 / 解码**双引擎** | 注意力结构不同 |
| 预填充注意力 | **原生子图** | 当时不改分页注意力的预填充支持 |
| 文本分词 | **不做** | 分词与数值是两个问题，混在一起无法归因 |
| 采样参数 | 温度 ≠ 1 **显式拒绝** | 静默忽略会让"调参无效"看起来像模型特性 |

## Technical Challenges

1. **弱类型网络下精度不能假定、只能查询**：引擎声明的边界精度与配置可能不一致，按配置分配
   缓冲会越界写，而且**单精度路径下永远不暴露**。
2. **所有权边界就是契约**：每层一对独立缓存；写 K/V 与推进长度必须拆开，且整步只推一次。
3. **缓存代次要手工声明**：指纹看不见插件源码变化，workspace 需求变化必须手工 bump 图版本。

## Trade-offs

- 双引擎换来各自最优的注意力实现，代价是两份引擎与两次显存占用。
- 循环内不同步（零拷贝）换来速度，代价是无法在循环内早停（EOS 只能循环后截断）。

## Interview Questions

### Level 1

Q：为什么预填充和解码要分开？　A：注意力形态不同：一个是整段带因果掩码，一个是单 token 读分页缓存。

### Level 2

Q：K/V 缓存在哪？　A：显存里，分页布局；每层一对独立张量，按块表和长度寻址。

### Level 3

Q：怎么保证解码循环不退化？　A：设备端维护长度，位置编码由它填；循环内不做同步拷贝。

### Level 4

Q：精度怎么处理的？　A：**向引擎查询**，不按配置假定；缓冲宽度、logits 行步长、cache 转换都按查询结果走。

### Level 5

Q：这阶段的已知缺陷？　A：FP16 端到端 NaN（层随构建变化），按政策不修、登记为已知限制，推荐用 FP32。

> **2026-10-06 更新**：撤销"不修"，转修复（依据 = 正确性：默认精度不可用即产品缺陷）→
> `docs/TROUBLESHOOTING.md` 18.2 与 `docs/dev/REQ-018-gpt2-fp16-nan/STATE.md`。
> **FP32 仍是当前可用的 workaround**，回答其余部分不变。
